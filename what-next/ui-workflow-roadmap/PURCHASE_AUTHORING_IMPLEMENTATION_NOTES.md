# Purchase-order authoring and creation recovery — UX14/UX15

Implemented locally on 4 October 2026. **Not released; application migrations unapplied, both application flags default off.** Fresh migrations and eight real PostgreSQL authoring scenarios now pass on the separate local test database; see `POSTGRES_WORKFLOW_VERIFICATION.md`. This is progress toward UC07, not closure of UX14/UX15 or the eight-use-case roadmap.

## Behavior

- Authoring work belongs to the current organization and creator. Incomplete date/numeric strings can be saved without a business purchase order, document number, inventory movement, payable or message. Saving uses an expected revision and exact-input replay hash; a stale second tab cannot overwrite a newer save.
- Preparing validates the saved fields, freezes the content, and stores a canonical command hash. The durable draft UUID is the creation request reference. A prepared payload cannot be edited under that reference.
- Creation validates current supplier, location and items inside the caller's transaction. Number allocation, business DRAFT order, existing BusinessEvent receipt, application marker and authoring result linkage commit together. The event has no outbox messages. Existing PO edit logic is retained.
- Status/receipt lookup checks current context and stored create permission, usable account, live session, purchasing module, organization and creator ownership. Receipt verification checks actor, entity, source, schema, event state, payload hash, canonical command hash, timestamp and minimal PO linkage. A recorded creation is resolved before write/admission gates, so disabling new work does not turn an existing result into a second creation.
- Discard first resolves recorded creation under the same locks. A committed order returns its receipt. An uncommitted draft becomes a retained DISCARDED tombstone, rejecting older create requests. Discard does not delete a business PO.
- Organization-first locking serializes authoring commands/status with organization policy changes. Draft locks and the existing organization/source/idempotency event key protect the result. Mocked checks do **not** establish PostgreSQL race correctness or throughput.
- The saved-work list is creator-scoped, bounded to 25 plus one, and uses database-native timestamp/ID cursors. Lists omit contents and receipt evidence; resume performs authoritative lookup. There is no browser-storage draft cache.

## UI and compatibility

`DurableCreatePurchaseOrderForm.tsx` is an isolated rollout variant of the existing form. Its recovery controls support English and French, save/resume/discard, explicit unsaved-work guidance, current revision and request reference, fixed failure messages and a separately verified creation receipt. Incomplete numeric input remains text; resumed item labels come from the current catalog, and unavailable references are identified. The subsequent localization pass covers wizard copy, validation messages, notifications, dates/currency, calendars and dialogs. Saved business text is preserved on resume. Quantity/price/tax/discount fields and item actions have record-specific accessible names; progress and current-step semantics are exposed, and navigation focuses the new step region. The installed calendar ignores labelDay, so full localized day names are supplied through its rendered day content. Real screen-reader/mobile verification remains open.

The form is keyed by server organization and actor. It suppresses duplicate clicks and stale unmounted responses. A lost save retains the exact input and key. A lost preparation/creation locks editing until status lookup; explicit creation retries query status before submitting the same prepared command. A successful receipt focuses its heading. The destination link requires the server-provided PO read capability; its destination continues to enforce current access.

The existing `ModernCreatePurchaseOrderForm.tsx` is unchanged from the pre-work index. Default `/purchase-orders/new` keeps its existing action and behavior. `PURCHASE_ORDER_AUTHORING_UI_ENABLED=true` selects the new variant. `PURCHASE_ORDER_AUTHORING_WRITES_ENABLED=true` separately permits save/prepare/create/discard. Neither was enabled. Other legacy create callers remain outside the new receipt contract; no system-wide idempotency claim is made.

Automatic approval review rejected replacing the default path with a write-disabled workflow because it could cause an outage. The accepted alternative preserves the original path and adds explicit opt-in. The temporary duplicated wizard should be consolidated after rollout acceptance, not removed while recovery gates remain open.

## Migration and rollout contract

1. Name a disposable PostgreSQL environment; apply the preceding access-request migration (compound User organization/ID key) and `20261004130000_purchase_order_authoring` there. The authoring table has compound creator/result foreign keys, revision/state checks, a creator paging index and unique result linkage. No backfill or purge is implemented. Restrictive foreign keys affect user/tenant deletion and need retention review.
2. Prove simultaneous create, create/status/discard races, transaction rollback after number/order/event/audit failures, revoked-session/role races, foreign actor/tenant probes and migration restore. Reuse actual services and two independent database connections. Verify one order, one number increment and one applied receipt, including after dropped responses.
3. Verify browser save/resume across tab closure and sign-out/in; expired/stopped/withdrawn permission states; stale catalog and multi-tab conflicts; keyboard, screen-reader, EN/FR and mobile tasks. Use representative restricted roles. Capture evidence without posting or approving business orders.
4. Measure the organization lock's effect on concurrent authoring and policy writers before choosing a cohort. Accept D07 retention/expiry and operating ownership. No automatic expiry is assumed; retain saved work and tombstones until an accepted data-preserving retention policy exists.
5. After those gates, enable writes and UI for the reviewed environment/cohort. Existing legacy paths must be inventoried before retiring them. Capture task baselines and pilot results under UX18/UX19.
6. Rollback: turn **authoring writes off while retaining its UI** to resolve prepared/completed requests. Do not route unresolved commands into legacy creation, generate replacement keys, reset sequences, purge receipts or drop the authoring table. Reverting the UI requires a reviewed recovery entry point for outstanding drafts.
