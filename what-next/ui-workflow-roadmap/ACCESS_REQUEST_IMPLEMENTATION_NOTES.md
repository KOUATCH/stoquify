# Access requests: UX12 foundation

4 October 2026. This is implementation progress within the full eight-use-case roadmap. UX12 and UX13 are not complete or released.

Follow-up: `ACCESS_REQUEST_UI_IMPLEMENTATION_NOTES.md` supersedes the schema-write blocker, missing history/UI and initial test-count statements below. The working schema is now integrated and validates; requester/reviewer screens and history are implemented, with 120 focused tests passing. Database deployment and release gates remain open.

## Implemented boundary

- New strict contracts, durable SQL lifecycle service, and authenticated server actions. The first normalized target is `items`, mapped on the server to `inventory.items.read`, the enforced inventory module, and `/dashboard/inventory/items`. Callers cannot supply a tenant, requester, reviewer, permission set, or redirect URL. More eligible denial targets remain to be registered and verified.
- Submission uses current stored account/organization validity, rechecks whether permission is already held, enforces the module boundary, and deduplicates an open request under the existing organization-first lock order. A database partial unique index backs the open-request invariant. A stable command hash detects conflicting replay payloads. Duplicate submissions return the existing request and its original reason.
- Request states are PENDING / APPROVED / DECLINED / WITHDRAWN / EXPIRED. Application states are NOT_REQUIRED / PENDING / APPLIED / FAILED. Approval stores the responsible reviewer and selected additions; it does not modify roles. Reviewer eligibility requires current stored and current-context read/assignment/target authority, with explicit assignment controls and no wildcard-derived grant ceiling. Self-review is rejected.
- Approval is fenced by request revision and the existing member/role-definition revision. Selected roles must be from this organization, assignable by the reviewer, and provide the requested permission. Existing roles are retained. Application uses the same saved command and reviewed role snapshot; stale state requires a new review rather than silently recomputing a broader grant.
- The existing `changeMemberAccess` implementation now exposes an internal transaction composition function. Its original organization/user/role/session locks, five-minute password assurance, self-change prohibition, current grant ceilings, last-custodian checks, session revocation and audit receipt remain in that function. The public wrapper retains its validation and transaction behavior. Both existing service and action regression suites pass.
- Role application, effective stored permission verification, the request's APPLIED receipt and the request audit event share one transaction. Failure recording is a separate revision-fenced transaction with fixed codes. A lost response after commit cannot change APPLIED to FAILED. Revoked reviewer authority may prevent recording a failure; the action does not invent a persisted outcome.
- APPLIED is historical evidence of a role change, not a permanent promise of access. The requester-only return action rechecks current permission and module availability before returning the fixed path. Sessions revoked by the member service require normal sign-in before that check can succeed.
- Requester lists are scoped before paging. Review queue requires current reviewer authority before querying requests. Pages contain at most 25 records and use a revalidated native database `(createdAt, id)` cursor. DTOs omit hashes, saved grant commands, role arrays, session proof and arbitrary errors. Audit entries contain lifecycle metadata, not request reasons or role payloads.

## Operating defaults awaiting acceptance

The optional D06 question remains pending. Implementation defaults are a shared eligible-administrator queue, named reviewer on decision, seven-day expiry for pending requests, and in-app status only. Pending expiry is materialized on scoped reads, duplicate submission, or withdrawal, using database time. There is no background expiry worker or email/provider delivery. Approved requests do not expire automatically; the requester can withdraw an unapplied approval and resubmit when a changed role snapshot or departed reviewer requires another review. These defaults are not an accepted operational SLA or retention policy.

## Migration and rollout status

- Added `prisma/migrations/20261004120000_access_requests/migration.sql`: additive request table, compound requester/reviewer tenant foreign keys, user compound unique index, list indexes, state checks and one-open-request partial uniqueness. No migration has run and no live grants have changed.
- Both `ACCESS_REQUEST_SUBMISSIONS_ENABLED` and `ACCESS_REQUEST_APPLICATION_ENABLED` default to false. Neither was enabled. Reads/decisions need the migrated table; UI integration must present unavailable storage honestly.
- Windows refused writes to the existing `prisma/schema.prisma` using both apply_patch and an escalated Node write (`UNKNOWN` on open). This was a filesystem error, not an automatic approval-review denial. The actual schema was not modified by this work. Its pre-existing changes are retained.
- The proposed schema was saved separately as `access-request-schema.prisma`; Prisma validation passes. `add-access-request-schema.cjs` contains the narrow insertion and creates the staged version with `--stage`. When the file-write issue is resolved, review and run its normal mode against the then-current schema. Do not replace the working schema with the full staged copy, since other work may have changed it. Regenerate the client only after actual schema integration.
- Compound user foreign keys intentionally prevent deleting or moving a referenced member/reviewer to another tenant while evidence is retained. Review this effect, index-build locking, and retention with the IAM/data owner before migration deployment. No backfill or historical approval inference is proposed.
- Rollback disables both submission and application flags while retaining requests and audit history. Do not drop the table or erase recorded grants as a rollback shortcut.
