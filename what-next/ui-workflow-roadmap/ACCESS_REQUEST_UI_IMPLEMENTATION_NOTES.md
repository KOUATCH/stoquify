# Access requests: UX12/UX13 follow-up

4 October 2026. This continues the full roadmap. It does not close the release or pilot gates.

## Current implementation

- `prisma/schema.prisma` now contains the proposed AccessRequest model and tenant-safe requester/reviewer relationships. Retrying the narrow insertion succeeded; the earlier Windows schema-write obstruction is resolved. The working schema passes Prisma validation. The draft migration remains unapplied.
- Prisma client generation first failed on a generated JavaScript file and then, with filesystem escalation, on the in-use Windows query-engine DLL. A separate read-only process successfully loaded `@prisma/client` and confirmed `Prisma.ModelName.AccessRequest`. This proves generated runtime metadata exists, not that the generator completed successfully. Complete engine regeneration in an isolated verification environment or during an agreed development-server restart. The current application was not stopped.
- New authenticated account route: `/dashboard/access-requests`. This placement deliberately allows a requester without `users.read` to see their own requests; review authority remains checked by each service. The original roadmap's settings path was a proposed location. The account menu provides a localized link, and the page component is keyed by organization, user, current permission set and selected task to discard prior-authority state.
- Registered item-list/item-detail permission denials can offer a localized request link with only `target=items`. A server helper verifies the current organization session and inventory entitlement before offering it. Expired authentication and module blockage do not offer the request link. New-submission rollout flag remains off.
- EN/FR requester and reviewer views show decision and application separately, request/reviewer references, pending expiry, reasons, withdrawal and safe task return. Before decision the owner is the shared eligible-administrator queue; on decision the reviewer reference is retained. Human queue ownership and operating acceptance remain open.
- Review preview now reads the request, usable member and complete role definitions within the organization-locked transaction, using the existing member revision and grant-ceiling functions. It returns all permissions for each assignable additional role and an existing-role count. The UI requires acknowledgement of complete selected-role permissions before approval. Approval still does not apply roles. A maximum of 100 total resulting roles matches the source member command.
- The request-specific history adapter authorizes the request first, scopes audit events to organization/entity/action family, selects only four lifecycle state fields, validates the projection, and paginates 25 events with a native database tuple cursor. It rejects a changed request revision and unavailable cursors. Raw audit payloads, reasons from unrelated records, hashes, role snapshots and network fields are not returned. Malformed state data receives an explicit limited-history presentation.
- UI commands suppress duplicate clicks and results from unmounted cards. List reads discard superseded queue responses. Revision changes clear prior review/history and move focus to the updated request heading. Submission retains the same command and reason for uncertain retries; requests are never persisted in browser storage.
- Password confirmation reuses the existing step-up action, clears the password after use, and requires a refresh and explicit application retry. It never automatically executes an approved grant. Current-access return is offered only on the requester's applied request; its server action rechecks current permission and module availability before returning the fixed localized destination.
- Module failure, session expiry, missing organization, denied authority, stale state and unavailable service have distinct fixed error classifications/copy. A failed action does not print arbitrary server error messages.
