# Development capability contracts

This read-only source audit defines 25 operational responsibilities. Permission eligibility is only one condition: module authority, tenant/location scope, distinct actors, workflow state, evidence and real human appointment remain separately required. No database data, roles, names, permissions or application code changed.

The JSON supports the parent live people/role join. Intended role codes are hints, not allowlists. Consider existing people before synthetic personas, but a supplied name or HRIS profile does not establish appointment or qualification.

## Findings

- Use actual `hasRbacPermission`: wildcard excludes high/critical operations. Role/member controls additionally need explicit stored authority and per-role grantability.
- Both inventory adjustment actions require `inventory.stock.adjust`; `inventory.adjust.approve` alone cannot post. Service actor separation remains mandatory.
- AP and payroll payment request/approve/release each need three actors. Payroll preparer/reviewer/approver also need three. Reviewer can technically post if separately permitted because posting excludes preparer and approver.
- Branch scope needs `dashboard.read` plus accepted tenant-wide authority or an actual active `Location.managerId` assignment. A manager role name alone is insufficient. Signer differs from starter.
- Cross-tenant accountant access needs exact current client consent. Read-only grants cannot export or review. Firm names and qualified-role names do not establish qualification.
- AI product/security approvers differ. Internal activation requires current certification, manifest/commit matching, accepted primary/distinct backup coverage and valid activation window. `ACTIVE_INTERNAL` is not production authority.

## Module boundaries

Inventory adjustment enforces inventory; AP payment service enforces purchasing; payroll transition actions enforce payroll; branch close enforces dashboard; POS opening/commit enforce pos and admission policy. A missing effective grant can block an otherwise permission-eligible account. Member-access settings checks are observe-only. No module gate was found in audited journal/close-certify operations; close dashboard separately enforces close_assurance. Do not infer enforcement from logical domain or equate selected/requested modules with current write grants.

## Minimum distinct responsibilities

- Stock adjustment/manual journal: at least 2. Preparer and poster differ for each record.
- Supplier payment: at least 3. Requester, approver and execution recorder differ.
- Payroll prepare/review/approve/post: at least 3. Three actors through approval. Reviewer can technically post if separately permitted; not an appointment recommendation.
- Payroll payment: at least 3. Requester, approver and releaser differ.
- Branch close: at least 2. Review starter and signer differ; both need actual scope.
- Certified close: at least 2. Runner and certifier differ; evidence/review requirements can require additional people.
- AI approvals: at least 2. Product/security approvers differ; owner/backup coverage is an additional requirement.

These are workflow minimums, not a reason to invent more roles/people. Existing people can hold compatible responsibilities subject to record-specific conflicts and real appointment/qualification.
