## How this relates to the forms you already have

Use the existing [approval-register start guide](<E:/ohada saas/Focused projects/stoquify/docs/approval-register/STOQUIFY_APPROVAL_REGISTER_START_HERE_2026-09-03.md>) and [Astra owner actions](<E:/ohada saas/Focused projects/stoquify/docs/Astra/USER_ACTIONS.md>). This file narrows the choices for module composition; it does not replace X1's approval contract or add another signature form.

When the recognized register is operational, the authorized person reviews the exact request version and records the real decision. The register generates the issued approval ID, verified signing timestamp, verification/event reference and permanent signed-record URI. Copy those generated values into the matching X1 fields. Reuse a URI only if that record exposes the corresponding value and verification evidence. A draft path, hash or local simulator identifier is not an authenticated approval reference.

Actual X1 completion still depends on the scoped decision and technical evidence meeting the approved contract. This composition design neither lifts X1 nor blocks ordinary local design/coding while the owner supplies missing information.

## Assumptions to revisit during implementation

- The next proof uses existing reconciliation with finance/accounting, preserving current required edges.
- Stoquify initially remains one deployment/database with explicit domain ownership.
- The internal financial integrity capability is included with activity that needs it; specialist workspace packaging remains a commercial decision.
- Existing client rights are reconciled and preserved during migration unless an authorized, explicit change applies.
- The first supported modules are internal application code. Executable third-party extensions and a marketplace are separate future scope.
- The illustrative five recipes, module versions and meters are design examples. They are not current subscription claims, approved prices or certified country coverage.
