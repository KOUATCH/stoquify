# Independent reconciliation sign-off — current operating guide

Open `/en/dashboard/finance/reconciliation` or `/fr/dashboard/finance/reconciliation`. The manager action center can also open a particular ready run. That shortcut discovers work; the destination checks current authority and evidence again.

## Inputs and responsibilities

| Needed | Supplied by / where to get it |
|---|---|
| Active workspace identity and reconciliation read/sign permissions | Your organization administrator, through existing user and role administration |
| Reconciliation write eligibility, including finance/accounting dependencies | Your module administrator, from actual tenant grants and validity periods |
| Ready run and current evidence | The reconciliation operator and reviewed-run preparation workflow; select the run already stored in Stoquify |
| Independent signer | An eligible person appointed by the organization, distinct from the maker and any disqualifying preparation/source-recovery actor |
| Open accounting period and active provider/approved effective settlement account | Accounting and provider administrators, through the existing setup workflows |
| Fresh authentication | Your own account password when prompted; never enter another person's credentials |
| Certificate/event/reference IDs | Generated by the application from persisted records; do not invent or replace them |

No product approval form or X1 reference substitutes for these reconciliation controls. Signing records an application reconciliation decision; it does not issue a payment or statutory certification.

## Review and sign

1. Open the run's independent review. Check provider, date, current evidence, counts and amounts. Amounts cover the full source population even where a detail table is paginated.
2. Review each currency and source category separately. Provider callbacks and statements may describe the same payment, so do not add those categories together. Current unresolved suspense excludes resolved/written-off cases; historical run totals are identified separately.
3. Resolve any reported prerequisite through its owning workflow. An error loading evidence is a failed review, not evidence of zero records.
4. Confirm only the displayed revision. If authentication is required, confirm your password, then explicitly activate **Retry**. Successful authentication alone does not sign.
5. Inspect the persisted signed state and use the authorized certificate export. The export receipt binds the downloaded JSON to its certificate hash; it is not a new approval.

## Failure, correction and history

- Wrong password: the field clears and focus returns so you can try again. Authentication failure is distinguished from an uncertain signing result.
- Interrupted/uncertain submission: keep the retained request and retry it, including after reload. Do not create another approval to compensate. The server returns the existing signature or identifies another signer's completion.
- Changed evidence: refresh and examine the current run before a new confirmation. A stale revision cannot authorize a new signature.
- Revoked role/module authority: stop and have the appropriate administrator review actual permissions or grants. Restoring access permits a new check; it does not bypass independent review. Read-only access never authorizes signing.
- New evidence after signature: use reviewed source incorporation. The original certificate remains retained, the run returns to review, and a new independent signature is required. Existing allocations are preserved.
- Incorrect approved source interpretation: use independent source-decision withdrawal, then investigate, prepare and sign again. Withdrawal itself does not reverse money or create a journal. See [source withdrawal procedure](RECONCILIATION_SOURCE_WITHDRAWAL_2026-09-27.md).

## Background observation and rollout

Signing atomically records its audit, business event and notification outbox message. The existing command `scripts/reconciliation-sign-notification-worker.ts` publishes the signed observation to the reconciliation inbox. `SENT` means a durable inbox observation, not that somebody read it or an external channel delivered it. The observation describes retained history; inspect the current run before acting.

The platform operator obtains the authorized database target from deployment configuration, organization ID from the tenant registry, and unique worker ID from the job host. Run and monitor the command using the invocation in the [handoff runbook](RECONCILIATION_SIGNOFF_HANDOFF_VERIFICATION_2026-09-27.md). Transient failures retain attempt count, safe error and `availableAt`; retry after that backoff. Lost acknowledgement does not create a second observation.

No live schedule was installed or production release authorized. Scheduling/monitoring and general exhausted-message or invalid-evidence recovery remain open under `NTF-DELIVERY-MONITOR` and `NTF-DELIVERY-RECOVERY`. Never manually mark a message delivered or alter its evidence hashes. Those operations require their own reviewed recovery process.

No schema migration is required for the current signing corrections. Roll out under existing controls with tenant grants and independent identities checked in the authorized cohort. If recovery is needed, stop new writes/worker execution as appropriate and retain certificates, receipts, audit, outbox and pending request identities. Do not revert the transaction guards or discard retained records to make a blocked run appear ready.
