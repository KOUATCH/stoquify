## Acceptance criteria

- Restore unsent selection, reasons and reviewer notes after reload under the same server-derived actor, organization, period and request.
- Reuse existing tab storage; validate its untrusted contents, bound input size and expire restoration after 24 hours since the last save. Exclude passwords, confirmation checkboxes and operational/approval assertions.
- Persist a strict pending command before dispatch; after interruption restore its exact idempotency key and require explicit retry. Never submit automatically.
- Re-inspect current evidence before restoring the form. Changed evidence must require current-source review before a new proposal; retain the original pending command for authoritative replay/refusal.
- Clear completed/discarded drafts and report unavailable storage while preserving in-memory work.
- Verify actual EN/FR reloads, a committed request with its response deliberately lost, no duplicate proposal and continued independent authorization/normal evidence acceptance.

## Implementation

New `hooks/accounting/close-evidence-resolution-draft.ts` uses strict shared command schemas from `services/accounting/close-evidence-resolution.schemas.ts`. Existing server exports are preserved. This moves validation declarations without changing domain rules. The recovery form persists only input fields and pending intent in the established tab storage pattern. It restores no confirmation, password, permission, approved status or trusted result. The investigation remembers only the last request reference; reloading still requires an authorized fresh inspection before draft contents render.

Scope keys use server-returned organization/actor identity and encoded period/request IDs. Identity/period changes remount the investigation; request/snapshot changes remount the form. Successful operations remove the submitted fields while synchronously preserving unrelated unsent input before the parent re-inspects. Explicit discard clears the draft only when no unconfirmed command needs reconciliation. An unknown outcome retains its exact input/key and makes new commands unavailable until resolved. Stored records are untrusted convenience data; server checks remain authoritative on every write.

Restoration expiry is checked on access and invalid/expired records are removed then. Session storage is not encrypted or a cross-device draft service. Same-origin code can access it; browser session restoration may retain tabs. The interface warns against shared browsers for private notes and reports storage failure. This milestone does not certify browser secrecy or immediate erasure when a timer expires.

## User instructions and rollout

Use `/en/dashboard/accounting/close` or `/fr/dashboard/accounting/close`. After reloading, select the same period if necessary and inspect the remembered request reference. Obtain missing references from retained evidence history or the colleague responsible for the request. Current authorized inspection loads the source before any matching draft is restored.

Review the restored selection and notes. Confirmations are intentionally unchecked. If the evidence changed, compare the saved selection with the current records and acknowledge that review before recording a new proposal. This acknowledgement is not approval. An unconfirmed submission instead offers **Retry saved submission**; use it to obtain the server's retained result or current refusal. Neither restoring the page nor password verification automatically submits the command.

The application retains only draft input and its pending command in this browser tab, with an expiry check. It is not an approval register, cloud backup or cross-device workflow. Discard a draft explicitly when no submission is pending. If storage is unavailable, the message explains that work survives only in memory; keep the page open while resolving it. Private review notes should not be entered on shared browsers. Existing proposal and authorization records remain durable server records regardless of local draft removal.

Ship the schema declarations, draft helper and affected components together. There is no database migration or server draft model. Removing this UI feature loses reload convenience but does not change approvals or source evidence; preserve the existing server idempotency and authorization controls. No deployment, reset, live customer action, payment or external delivery occurred.
