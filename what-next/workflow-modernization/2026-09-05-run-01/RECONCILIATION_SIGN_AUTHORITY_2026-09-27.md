## Demonstrated defects and corrections

The review service required both reconciliation read and sign permission, while the signing service accepted sign permission alone. A focused regression reproduced a successful certificate after read permission was withdrawn. Signing now also requires read permission; its transaction verifies an active actor in the same organization before reading or changing the run. Concurrent-sign recovery repeats the active-actor check. Existing server-derived identity, fresh authentication, module enforcement, independence, evidence-revision and transactional controls remain effective.

The open review also kept evidence and authentication state when its permission prop changed. Deferred preview, signing and authentication regressions reproduced stale response handling. The component now remounts its review session on tenant, actor, run or authority changes. This clears visible evidence, certificate and password state and retires the old session's responses. A restored session rereads authoritative evidence. The exact uncertain command remains in scoped session storage; it is never automatically signed on restoration.

A real Chromium contrast check found the primary sign label at **2.99:1**, below the 4.5:1 normal-text target. The correction uses the existing daily-digest treatment: darken both ends of the dashboard brand gradient, retain the hover treatment and show an explicit focus outline. A local CSS module limits the change to sign review.

## Operator guidance and recovery

Open `/en/dashboard/finance/reconciliation` or `/fr/dashboard/finance/reconciliation` and review the selected run. The signer needs current read and sign permissions, an active account in this organization, the required module access and independent-actor eligibility. Password confirmation refreshes authentication; the user must still explicitly confirm the retained request.

If access changes, the review is withdrawn. Ask the organization's role administrator to review the actual role assignment/account status. Restored authority rereads the run; retry the same retained request to resolve an uncertain outcome. Do not create a second run, fabricate approval evidence or erase an uncertain command merely to bypass a denial. Certificate export still has its separate server authority checks.

No schema migration is required. Release through the existing deployment controls. Preserve retained certificates, security records and pending request identities during recovery; reverting to the earlier authority implementation would reintroduce the reproduced gap.
