It does not complete either workflow, clear X1, authorize deployment, or establish accounting, security or release certification.

The correction requires current writable Accounting authority for manual reversal and preserves the actual age of the action's verified authentication. Previously the action supplied `Date.now()` as `lastAuthAt`, and neither the action nor reversal service checked the module grant. ## Authority, retention and transaction order

The action fixes Accounting `write` access with `mode: "enforce"` at `actions/accounting/journals.actions.ts:137`. It binds the fresh-authentication claims to the permission context's actor and tenant, passes the verified `lastAuthAt` at line 155, and constructs its callback on the server. Browser fields cannot replace the module policy, actor, permissions, timestamp or callback. After preparation, that callback rechecks `requireFreshAuth(300)` and `requirePermission("accounting.journal.reverse")`, including actor/tenant equality. Identity mismatch raises an internal `UNAUTHENTICATED` error that the canonical transport maps to `AUTH_REQUIRED`/401 (`lib/error-handling/canonical.ts:304`); missing writable module authority produces `FORBIDDEN`/403. Existing protected-action handling maps fresh-authentication failures to `FRESH_AUTH_REQUIRED`/403.

The service evaluates persisted module authority before catalog, journal or period locks (`posting.service.ts:463`). The reused evaluator (`module-entitlement.service.ts:172`) holds the active, nondeleted organization for SHARE, then configuration and deterministically ordered grant rows for SHARE. The owning transaction remains Read Committed. Module configuration writers use the organization's UPDATE lock first, including the first transition from legacy intent to managed grants. A managed empty grant set remains a denial; valid legacy defaults retain their existing meaning. Wildcard RBAC does not override grants, and validity is assessed with real wall-clock time rather than the optional accounting test clock.

The rest of the order is unchanged: shared tenant catalog boundary, tenant-filtered original journal `FOR UPDATE`, fresh original read, sensitive admission, existing source and suspense guards, open reversal-period check, then the existing sorted affected-period assessment locks. After those waits, sensitive freshness is checked before invoking the authority callback. The callback is followed by another module evaluation and a final sensitive check before the allow audit and first batch write (`posting.service.ts:574–584`). This final check also accounts for time spent in the callback or grant read. No grant, session or permission result is accepted from browser input.

Stopping new work is not a grant withdrawal. `module-stop-policy.service.ts:25` and `:34` retain existing accounting work and mandatory ledger effects; `module-admission.service.ts:56` explicitly excludes correction from the new-work gate. This patch does not call that gate for reversal. A stopped workspace can still correct an existing manual journal when its current grant is writable and all existing accounting controls permit the correction. Missing, future, expired, suspended, `read_only`, or `readOnly: true` authority is denied.

No new lock inversion was identified in the reviewed module configuration, fiscal-period, close-period and suspense reservation paths. Module writers take organization UPDATE before their observations; fiscal child foreign-key KEY SHARE locks are compatible with the authority SHARE lock; the reviewed accounting paths do not subsequently demand an opposite organization UPDATE lock. The additional authority locks remain held through the financial transaction and can increase waits for module changes. Production contention and capacity have not been measured.

## Deliberate audit and financial behavior

The earlier initial `JOURNAL_REVERSE_CONTROL` allow audit has moved to the final successful admission boundary. An early sensitive denial or post-wait freshness denial records only `JOURNAL_REVERSE_CONTROL_DENIED`. A module denial records `MODULE_ENTITLEMENT_ENFORCED`, returns without business effects so the denial audit can commit, then throws `ForbiddenError` outside the transaction. This is deliberate: a denied attempt must not leave a premature allow audit that looks like completed authorization.

Source-owned journals still commit `JOURNAL_ENTRY_SOURCE_OWNED_REVERSAL_BLOCKED` and refuse generic reversal. Suspense clearing/recovery reservations, non-posted or already reversed journals, missing functional-currency values, unbalanced lines and invalid periods retain their existing refusals. Callback exceptions and authority-storage exceptions abort the transaction; this review does not claim a separate persisted service denial audit for those failures.

Successful reversal preserves the original journal and its lines, adds one governed mirror with the original transaction/base amounts and dimensions, links the new batch and source, and invokes the existing ordered Close invalidation. The patch does not enlarge its affected period scope or change financial compensation. Repeat attempts continue to refuse a second reversal.

## User recovery and operational boundaries

Use the existing manual journal reversal action for a manual posted journal. Provide the target journal, a meaningful correction reason and an allowed reversal date. The server supplies identity, permissions, module state and authentication proof. A source-owned journal must use its domain correction workflow, not this manual command.

For a module denial, an authorized module administrator must inspect the actual Accounting grant, status, read-only flag and validity interval. Restore access only through the recognized process, then retry the same original journal. For fresh-authentication or changed-session refusal, re-authenticate and reload the correct organization. For permission refusal, obtain the required authorized role and preserve separation of duties. If a request times out after possible commit, reload the original journal first: a completed reversal is retained and a repeat must not create a second compensation. Storage failure calls for restoring the failing service and retrying, not replacing failure with an assumed success.

No schema migration, backfill, provider change or live activation is introduced. Before any separately authorized rollout, bind the target build to terminal current-source verification and review unresolved Close scope separately. If selective code recovery is authorized, compare the four reviewed hashes before restoring their exact predecessors; preserve concurrent changes and existing financial records. Reverting this correction reopens the entitlement/freshness gap. Reversals that already committed remain accounting history and must not be deleted to simulate code rollback.
