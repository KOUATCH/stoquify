# Supplier payment request and review workspace — v81

## Delivered experience

The AP workbench now links authorized users to two application pages:

- `/{locale}/dashboard/purchases/payables/payments/request`
- `/{locale}/dashboard/purchases/payables/payments/approve`

Use `en` or `fr` for the locale. Both routes inherit the authenticated application shell and explicitly enforce purchasing access and their respective payment permission. The server-owned read models revalidate current database identity, organization, roles and session before returning records. A client draft does not establish payment authority.

This batch extends the verified v80 request/approval controls with source selection, current balances, paged queues, review, password assurance, exact retry recovery and request/approval history. Payment release, rejection/withdrawal, legacy approval recovery and external reconciliation remain separate unfinished work. The full platform workflow review is not complete.

## Requester procedure and required information

1. Open **AP Workbench → Request a supplier payment**. Your administrator assigns `purchasing.ap.payment.request`; the AP workbench also requires its existing read permission. A directly opened request route uses the request permission and purchasing module gate.
2. Find the supplier from existing active supplier records. Select an approved destination from its masked bank/mobile-money records. If a destination change is pending, finish the existing independent bank-change approval process first. The requester cannot approve a destination on this page.
3. Select eligible posted or payment-pending invoices. Enter the amount allocated to each. The displayed available amount subtracts recorded payments and net posted credits. Use one currency per request. The preview does not reserve money, and the server checks the balance again on confirmation.
4. Enter the intended method and payment date from the payment instruction. Link the retained supporting document that the approver can access. Choose that exact file to compute SHA-256 locally, or paste its existing hash. Files up to 20 MB are supported for local hashing. The file itself is not uploaded by this control. Neither a hash nor a link proves who signed a document.
5. Add any notes needed by the approver. Review the supplier, masked destination, date, method, exact allocations, document reference and hash before submitting. Verify your current password if requested.
6. A successful submission reports **Awaiting approval** and appears in **My payment requests**. It does not report a release or bank settlement. Keep the record reference for follow-up.

Only an administrator or designated organizational owner can supply missing role authority, approve bank changes, or establish the real source-document register. These inputs are not generated by the UI or by these tests.

## Independent approver procedure

Open **AP Workbench → Review supplier payments** with `purchasing.ap.payment.approve`. The initial queue shows drafts. Search by request or supplier; use **Include other states → Refresh requests** to inspect other recorded states.

Choose **Review this request**. Confirm that the stored instruction, destination and allocations reflect the intended payment. The system checks current balances and evidence, and blocks self-approval. Verify your password if needed, then approve the retained request. Approval updates the same payment record. Release and reconciliation are still separate processes; this page executes neither.

**Request and approval history** shows the current state and verified request/approval timestamps. Missing or inconsistent evidence is explicitly unverified and requires investigation. A source-query failure is an error, not an empty queue or an approval. An earlier approved state is not evidence that funds settled externally.

## Drafts, stale data and uncertain outcomes

Unsubmitted drafts and exact retry commands are retained in session storage under the organization, actor and operation. Passwords are never persisted with the draft. Changing the active identity replaces the workspace and invalidates late asynchronous responses; denied access clears private in-memory state and that workspace’s stored draft.

If an invoice, credit, destination or other reviewed source changes, confirmation rejects the stale revision. Your entered draft remains available. Refresh and review current terms before a new confirmation.

If a response is lost, reload and choose **Retry the same confirmation**. The retained key allows the server to return the existing outcome. Do not create a new request merely because the original response was unavailable. If session storage cannot retain the retry command, confirmation stops with guidance rather than proceeding without recovery information.

An unresolved reference conflict requires review of the retained request. Requests cannot yet be rejected, withdrawn or replaced through this workspace. Do not erase events, forge approvals or change database rows to force a retry through.

## Design-system mapping

The pages reuse the purchases route wrapper, AP workbench entry point, dashboard theme/content classes and `--dash-*` tokens. Shared Button, Input, Label, Textarea and Dialog components are retained. Selections use brand color; review warnings use warning color and text/icons. Awaiting approval, approval and release/reconciliation are named separately. No selected invoice is styled as an approved payment.

The review overlay inherits the dashboard theme, constrains its height, scrolls its contents and returns keyboard focus to its opener. Forms stack at narrow widths. Text wraps for French labels and references. Reduced-motion preference and 200% text reflow are exercised; actual assistive-technology certification and native browser zoom testing remain unclaimed.

Payment strings live in `messages/payment-request/en.json` and `fr.json`. Both the server i18n configuration and the locale layout’s client provider include the namespace. The first browser run found the missing client-provider integration and is retained as failed evidence; the correction is not inferred from unit tests alone.
