## Defect and delivered behavior

v131 confirmed that the financial service could replay an immutable committed response without new effects, but the tender action's write gate prevented retrieving it after commercial access loss. The cashier also retained only an in-memory identifier, lost on reload. Retrying from a new cart could obscure an earlier unknown result.

`getPOSSaleCommitStatus` is a separate service read, reached through `actions/pos/commit-recovery.actions.ts`. The action requires current `pos.read` and server-derived tenant/cashier identity. It does not require authority to create a new sale. The service matches original tenant, actor, store, terminal, session, sale and client identifier, verifies the original request hash and stored result hash, and reads current sale status in a repeatable-read transaction. No commit function, receipt completion, financial mutation or delivery runs through this path.

Outcomes remain distinct: `NOT_FOUND` means no matching result was found, not proof that an earlier request stopped; `PENDING` identifies an unfinished claim; `RECORDED` carries a verified original result summary plus current sale status. A later void/refund is visible as current state rather than being hidden by the original completed response. A failed or inconsistent read returns failure, never a successful missing-result state. The action's ordinary permission audit remains separate from financial effects.

The cashier retains the original request in session storage, under an organization-and-actor-specific key, before sending it. Stored data is parsed and scope-checked on reload. The original tender, customer reference, receipt locale and commit identifier are reused for explicit retry; new edits do not silently replace the request. No credentials or access tokens are stored. This browser record is recovery input, not authority or proof of payment. Server identity, hashes, idempotency, tenant boundaries and current write controls still decide every operation.

An unresolved request blocks a new submission. A cashier can check its result; only a missing exact result offers explicit original-request retry, still through existing write permission and transaction checks. A recorded result requires acknowledgement before clearing local recovery. A synchronous in-flight guard prevents rapid clicks from creating multiple request identifiers. Storage failures pause submission and retain an actionable error.

The EN/FR panel uses existing attention/brand tokens, text outcomes, live status announcements and explicit buttons. First appearance/restoration focuses the panel and scrolls it below the sticky header. This corrects the first mobile capture, where the header obscured part of the recovery heading. No application shell or shared design system was replaced.

## Cashier and support procedure

Open `/en/dashboard/pos` or `/fr/dashboard/pos`. If submission has an unknown outcome, keep the tab open. After reload the recovery panel shows the original request reference. Choose **Check previous result**. Checking is a read; it never charges, posts or sends a receipt.

If recorded, review the sale number, amount and current status. Acknowledge the reviewed result to clear this tab's pending request. If no exact result is found, do not assume the earlier process stopped: the offered explicit retry sends the same retained request and identifier through current authorization and idempotency controls. Grant restoration itself does not submit. Failed checks or unfinished claims remain unresolved and can be checked again.

An authorized support person needs organization, cashier, request reference, store/terminal/session, approximate time, and any correlation reference from the failure. Obtain the request reference from this panel; scope comes from the authenticated workspace and retained request. Verify server commit registry, current sale, payment, posting/source links and audit records. Never infer completion from browser storage or invent a commercial approval. Restoring `pos.read` requires the normal authorized role-management process; this batch does not grant it automatically.

Storage is scoped to the current browser tab: reload and same-tab reauthentication are supported; closing the tab, clearing browser data, another device or storage corruption still requires support-assisted lookup. That gap remains engineering work for a discoverable retained-history flow. Do not clear browser data as a recovery shortcut. Retained original inputs are cleared after confirmed success or reviewed recorded outcome. They are not an offline entitlement, payment credential or durable cross-device ledger.
