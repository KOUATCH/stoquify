## Verified starting contract

The historical graph identifies the journal page and its `sumLines`, post and reverse functions in `graphify-out/graph_app.json`, community 17, node `locale_dashboard_dashboard_accounting_journals_page_tsx`; `graph_actions.json` community 38 contains `accounting_journals_actions_listjournalentriesaction`, `accounting_journals_actions_postjournalentryaction` and `accounting_journals_actions_reversejournalentryaction`. Important relationships below were verified against current source rather than the graph's historical line positions.

At discovery, the journal page SHA-256 was `09275372b3bf8e445d0ee8bc3ce31da59dbfbb4cd25b3faf1897f2ca506c3de7`. The unchanged read service `services/accounting/journals.service.ts` was `c8134774870509bf849d252eba9632abe55bb35e59fded9c4d5e01fc9c64535e`.

`listJournalEntries` (line 284) reads tenant-filtered journals, including their journal, period, posting batch and complete ordered lines. Each line carries its own currency, nominal debit/credit, exchange rate and nullable base debit/credit. The Prisma amounts are Decimal values, not plain client DTO numbers. The list action derives the tenant from the server permission context. The page asks for the newest 100 rows across all statuses; its draft/posted counts are therefore counts within this loaded slice, not totals across the organization. `VOIDED` records exist in the schema but the original two panels omit them.

The original `sumLines` added nominal amounts across currencies and passed the result to `formatAccountingMoney`, whose defaults label it XAF, use French formatting for either locale, round to zero decimal places and replace nonfinite input with zero. That is not a truthful journal-evidence presentation. `JournalEntry.currency` cannot repair it: draft creation stores the first prepared line's currency there (`journals.service.ts:361`), and the service explicitly supports mixed-denomination journals. For example, 100 EUR and 100 XAF are separate nominal totals; they are not 200 XAF. The base amounts also cannot be labeled from this header: their denomination is the organization's accounting base currency, which is absent from this list DTO.

A bounded correction is to group nominal totals by each persisted line currency, preserve exact two-decimal arithmetic and format each group for the actual locale. Missing/invalid values must remain unavailable, not zero or an assumed XAF amount. Displaying functional-currency totals instead would require the authoritative accounting base currency and complete base amounts. That is a separate read contract. `prisma/schema.prisma` defines both nominal and base amounts at Decimal(18,2); the existing zero-decimal helper should not be changed globally merely to fix this page.

## Actions and honest failures

`withAccountingSurfaceAccess` already supplies a trusted `RbacContext` to `onAllowed`; the original page discards it. `checkPermission` returns only a boolean. Render-only create/post/reverse flags can use `canUsePermission(context, permission)`, which preserves canonical wildcard semantics. These flags improve the interface but never establish authority: the post/reverse actions and transaction services still recheck permissions, module grants, freshness and accounting controls.

Both posting and reversal require the exact `MANUAL` source type. Null, unrecognized or domain-owned sources must not be offered a generic manual mutation. Reversal additionally refuses completed reversals and reserved suspense clearing/recovery journals. The list includes `postingBatch.metadata.resolutionRecoveryReceiptId`, which can explain a known source-recovery restriction. It does not include the suspense allocation lookup used by the service, so a visible button must not promise that a journal has passed every server control. The read route currently declares journal-read permission without a module-read gate; this UI correction must not silently redefine retained historical-read policy.

The original page converted failed queries to empty arrays and displayed zero counts and empty-success tables. A failed journal-entry query must display unavailable/error state, omit misleading zero counts for that source and preserve a retry action. A genuinely successful empty result remains a distinct state. One failed read must not invent results for the other source.

Recovery should preserve the selected journal and entered reason after a recoverable refusal, explain fresh-authentication/module/permission failures in EN/FR, and require an explicit new submission after authentication succeeds. A timeout or lost response must offer a way to reload authoritative state before retrying a consequential action. Server-owned reversal safeguards prevent a second completed reversal, but the client must not present a transport failure as proof that no commit occurred. Buttons, dialogs, status announcements and busy states must remain keyboard-accessible and use the existing dashboard theme and semantic colors.

A further review finding concerned the refresh button: previously it cleared a refusal before `router.refresh()` delivered any authoritative data. The corrected page supplies a new server nonce only after a successful journal-entry read, and null after failure.
