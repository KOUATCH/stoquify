## Behavior and controls

A reviewer can propose the retained request, optional response and optional acceptance that should govern processing. Every other workflow record requires an explicit exclusion reason. The proposal is bound to the inspected snapshot, all retained source hashes and the previous recovery authorization. It is persisted as `CLOSE_EVIDENCE_HISTORY_PROPOSED` in the existing organization-scoped ledger audit journal. Recording a proposal changes no finding or source evidence.

Authorization requires another current reviewer who did not author any selected evidence. Both proposal and authorization require current module write access, Close read/review permissions, the authenticated server session and recent password assurance. Existing authority locks and post-wait/commit revalidation are reused. Approval is persisted as `CLOSE_EVIDENCE_HISTORY_APPROVED`, with the proposal, approver, review notes and exact source binding. A hash is not treated as a signature or authority.

Finding locks and the previous-authorization binding prevent competing decisions from both succeeding. Idempotency keys preserve exact retries; changing intent under the same key is refused. Source changes after proposal require a fresh inspection. The application rejects self-authorization, selected-source authors, incomplete snapshots, missing/changed decision history and invalid selections.

Selections must match the finding's current status, ownership, period, assessment and linked evidence. Recovery does not change the finding status or create an evidence acceptance. A structurally valid recorded acceptance cannot be discarded to restart work. A malformed legacy row labelled as an acceptance may be explicitly excluded by independent review while retained; it does not establish an accepted outcome. A valid already accepted chain may be selected only when its retained acceptance matches the existing resolved finding and replacement binding.

The same resolution reader now feeds both variants of the recipient and accountant review queues, response/acceptance writers, recipient replacement and requester tracking. It verifies the retained proposal/approval link and hashes before applying exclusions. New records remain visible, so earlier authorization never silently excludes later evidence. Changed or missing bound records invalidate the selection. Excluded requests are labelled as retained and superseded in requester history.

The EN/FR forms use the existing dashboard controls, focus treatment, borders and responsive layout. An uncertain submission retains its in-memory draft and exact command for explicit retry. Password verification does not automatically submit authorization. Read-only users can inspect history but cannot write a recovery decision. The original source records remain visible in investigation with exclusion labels and authorization references.

## Operating instructions and required information

Routes: `/en/dashboard/accounting/close` and `/fr/dashboard/accounting/close`.

1. Select the accounting period. Obtain the request reference from requester history or the colleague reporting the issue, then inspect the retained records.
2. A current reviewer selects the governing request and any linked response/acceptance. Use the record IDs and contents displayed in the inspection. Explain the overall decision and why each other record must remain retained but excluded from processing. These are factual investigation conclusions supplied by the reviewer, not facts generated by the assistant.
3. Record the proposal, completing password verification if requested and explicitly retrying afterward. The proposal reference appears under recovery proposals. This has not changed the evidence used for processing.
4. An independent authorized reviewer signs in, inspects the same request and proposal, checks the selected records and every reason, records review notes and confirms authorization. The proposer and selected-source authors cannot authorize it. The second reviewer must be a real person with organizational authority for live use; synthetic verification accounts establish no live approval.
5. Refresh the evidence workbench. Follow the existing response or independent evidence-acceptance action. Recovery authorization is not evidence acceptance, close certification, payment permission or X1 approval.

If evidence or a prior decision changed, inspect again and prepare a current proposal. For an uncertain response, keep the form and retry its saved submission. The proposal and approval audit records are durable and visible through the investigation history. Unsaved recovery drafts currently survive action failures in memory; reload persistence is not yet implemented. Do not resolve conflicting records by deleting them or modifying old audit entries.
