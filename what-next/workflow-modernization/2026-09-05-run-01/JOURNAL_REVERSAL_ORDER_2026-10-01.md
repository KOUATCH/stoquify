## Implementation and scope decisions

Manual and customer-settlement reversals now acquire a shared tenant accounting-catalog lock, select the open posting period under its existing row lock, resolve one complete tenant-owned period set, and acquire its assessment keys in sorted order before financial writes. The set includes both explicit period IDs, overlaps of **both original and reversal dates**, and all later periods from the earlier date when the original journal contains a class-3 account. Explicit foreign/missing periods fail before financial effects. Periods without an existing assessment remain in the lock set so an assessment cannot publish across an in-progress correction.

The original-date overlap extension was found during source review: the tenant operating snapshot counts POSTED journals by entry date and source links by source date; its metrics contribute to the hash retained in Close's payroll forecast evidence. Changing the original journal status and adding a reversal link can therefore affect an original-date-only overlapping period even without class-3 lines. Class-3 evidence additionally includes cumulative closing journal lines and journal status, requiring the later-period scope.

`recordOrderedReversedJournalCloseInvalidationsInTx` accepts the resolved set and discovers one deduplicated, globally ordered Close-run population. It refuses a set that omits either explicit period. It preserves the original source ID, reversal journal reference, stale reason, audit/outbox behavior and retained export contents. Manual reversal explicitly owns Read Committed. Settlement preserves its existing Serializable isolation and three-attempt retry budget: after catalog and assessment locks, it compares its snapshot's period membership/boundaries and eligible run IDs with fresh committed reads. A mismatch rolls back and retries the whole transaction before compensation. Already completed settlement requests still require exact replay evidence; repeated manual reversal remains a refusal. Both paths recheck authentication freshness after waits.

Four additional callers were exposed by the full TypeScript check: inventory adjustment reversal, purchase correction ledger, payment suspense correction and suspense resolution recovery. Their existing `recordReversedJournalCloseInvalidationsInTx` API and behavior are preserved. They do **not** acquire this new guarantee through the compatibility API. Their owning lifecycle/transaction contracts need explicit migration in a subsequent milestone; adding advisory locks late inside a shared invalidator would not establish correct ordering.

No financial source ownership, original decimal/base-currency mirrors, separation of duties, suspense reservation/recovery restrictions or exact-replay requirements are relaxed. No schema or UI change is included.

## Operating and recovery instructions

Use the source command appropriate to the original journal. For a manual correction, the authorized independent operator supplies the original journal, reversal date within an open period and reason, then completes fresh authentication. A customer collection must be corrected through customer-settlement reversal with its retained settlement ID, stable idempotency/correlation references and actual evidence hashes. A generic journal reversal must not substitute for reversing the source obligation.

If a lock wait outlasts authentication freshness, reauthenticate and submit the same intended correction. A concurrent evidence change can cause automatic whole-transaction settlement retry; after the bounded conflict, refresh the relevant state and retry the same request. Do not create a new idempotency key to bypass uncertain prior completion. Manual reversal checks persisted state and refuses an already reversed journal. A committed reversal deliberately makes affected existing Close evidence stale. Retain that history, run a new assessment, resolve actual blockers, and use an authorized independent certification flow for a new export. Never edit the old run or signed/exported bytes to look current.

The fresh committed reader needs a second available database connection while a Serializable transaction holds locks. The production Prisma configuration currently sets maxWait 10 seconds and transaction timeout 15 seconds; URL-specific connection-pool settings are deployment-owned. Pool starvation or fresh-read failure fails the correction instead of treating unavailable evidence as empty. The controlled race verifiers use longer local observation timeouts; their elapsed times are not production throughput or latency certification. Validate connection capacity and concurrent correction load in the authorized rollout environment before enabling a cohort. No capacity figure is invented here.

There is no migration to apply. Roll out the service code and both helper APIs together, retaining the old API until its four callers are explicitly migrated. Application rollback must preserve committed journal/receivable/history rows; do not delete compensation or invalidate evidence manually. Reverting to the predecessor reintroduces the documented concurrency/scope defect and is not a safe data-repair procedure. Stop new correction submissions at the approved operational boundary if rollback is required, inspect persisted outcomes and apply a forward fix. No deployment was performed by this work.
