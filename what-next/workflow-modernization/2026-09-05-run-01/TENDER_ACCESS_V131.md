## Reproduced defect and implementation

The three tender actions already enforced writable POS module access before calling their service; refunds/voids also required their specific permission and fresh authentication. Their financial transactions did not recheck module eligibility. Direct service execution, or an access change after action preflight, could admit new effects under a now read-only grant.

The owned database reproduction completed a cash sale, refund and void under read-only POS access with actual posting services. Final before report: `lanes/environment/tender-access-v131-before-0a06eeae-8855-4811-888c-79cc3da9d767.json`, receipt `4665df`. This is service-boundary evidence, not a claim that the ordinary action admitted a grant already read-only at action entry.

New `services/pos/tender-write-access.ts` reuses the transaction-aware module evaluator. `commitPOSSale` checks it after exact existing-result resolution and before new-sale admission. Refund and void check it before loading or changing financial records. Existing action guards, permissions, five-minute fresh authentication, domain invariants and stop semantics remain. Denial rolls back and records `POS_TENDER_WRITE_ENTITLEMENT_DENIED` afterward. Policy IDs: `pos.tender.commit/refund/void`, version `2026-09-13.1`; owner: POS domain services. An audit failure propagates, never succeeds or repeats a financial transaction.

The user's explicit instruction to repair demonstrated eligibility defects authorizes this bounded correction to existing enforced action policy. No shared observe defaults, commercial grants, country setup, live activation or unsupported stop controls were changed. The historical action graph locates `pos_tender_actions_ts` in community 133 and its tests in 56; current action/service source was verified directly.

The cashier now receives a persistent EN/FR inline access alert, preserving cart, tender and existing commit identifier. It describes this attempt as denied and asks users to resolve an earlier unknown outcome before trying again. It does not assert that an earlier request failed. Existing dashboard danger tokens and `role="alert"` provide non-color meaning. Hook notification suppression leaves this component responsible for feedback and avoids duplicate failure notices. Successful explicit retry clears the alert. No automatic submission follows a grant change.

## Operator procedure and remaining recovery boundary

Open `/en/dashboard/pos` or `/fr/dashboard/pos`. On denial, keep the cart/tender. The authorized administrator needs organization, cashier, operation, failure time and correlation/audit reference; obtain these from current session and action/audit records. They review current POS/dependency grants, validity and role permissions using the established process. A cashier must not manufacture an approval or edit production grants. For a confirmed denied first attempt, explicitly retry after authorized correction. A grant change alone does not submit.

If an earlier submission had an unknown outcome, do not start another sale. Authorized support must inspect the original commit identity, tenant, cashier, sale, result hash and payment/posting records. The exact service replay preserves the original committed response even if the sale was later refunded/voided; it is not a current sale-status read. Current action-level write gating still blocks that replay after access becomes unavailable. A dedicated safe recovery/read path and durable browser request persistence are still engineering work, not external approvals. Refund/void after loss of commercial access also require a supported retained-obligation policy; this batch preserves existing denial and does not invent that policy.

Release guard/service/UI/messages together through existing controls. No migration, deployment, real payment or X1 clearance occurred. Prefer forward correction or presentation rollback retaining financial admission. Removing the transaction guard reopens the reproduced gap. Production rollback rehearsal, full financial recovery and offline continuation remain outstanding; do not enable offline replay from this test (its current deployment guard remains in force).
