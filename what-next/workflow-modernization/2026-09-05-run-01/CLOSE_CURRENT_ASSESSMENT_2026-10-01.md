## Problem and implementation

The retained local receipt `lanes/environment/cash-close-recovery-readonly-4e711acb-b190-418a-826a-f6e8400bf410.json` showed a newly certified assessment in Close while Cash still combined it with an older invalidated assessment for the same period. The older observation never stopped contributing blocked/stale counters. Separately, actual zero-variance counts changed the inventory evidence fingerprint without invoking producer invalidation.

Cash readiness now uses one latest assessment per overlapping accounting period, ordered by creation time and then ID. Updating historical records cannot make them current. Latest RUNNING, DRAFT, BLOCKED and VOIDED assessments are included; the reader never searches backwards for an older successful certificate. Equal latest creation timestamps cause a dedicated blocking ambiguity condition with EN/FR guidance. ID ordering stabilizes display; it does not establish chronological precedence. Different period IDs remain distinct even if their date ranges overlap.

Current assessment state, checklist observations, export proof and readiness averages are separate from retained obligations. Unresolved historical findings in the selected period scope remain counted. Tenant-wide critical findings and unavailable evidence retain their existing wider scope. A new assessment does not resolve, waive, delete or rewrite these records. Historical exports, hashes, audits, comments and explicit old-run Proof Trail reads remain intact. `recentCloseRunCount` now counts current period assessments rather than all historical attempts; the public contract documents this meaning. Snapshot reads remain inside one RepeatableRead transaction and source hashes bind selection and retained obligations without exposing private IDs.

Default Close selection and Cash's Close proof target use the same creation-time ordering. Cash's related period predicate explicitly includes the tenant. Its single proof target represents that record; it cannot certify a multi-period aggregate by itself.

Zero-variance count posting now invokes the existing inventory invalidation service after the session is POSTED and its business event APPLIED, inside the same transaction. A replay returns before those effects. Stock and ledger amounts are unchanged. Inventory fingerprints include count events cumulatively through a period's end; this producer therefore opts into invalidating all periods ending on or after the earlier of the count date and event date, plus the posting period. This conservatively includes intervening periods when the dates differ. One tenant-scoped, ordered target query handles the set. Other helper callers retain their existing scope. There is no schema change or new delivery mechanism.

Audit review found that reusing the valuation-write source family would label a count-session ID as an inventory transaction. New zero-variance invalidation now uses `INVENTORY_PHYSICAL_COUNT_VALIDATED`, with `StockCountSession`, `stock_count_sessions` and `inventory.physical_count.validated`. The registry supplies those values consistently in run/export stale state, event, audit and outbox records. Existing valuation callers and retained records are unchanged. Independent source review found no defect in this narrow mapping or transaction ordering; delivery and full rollback verification are separate requirements.

The Close component also retains identity focus-return intent while permissions or pending mutation state keep the originating action disabled, consumes it once after focus succeeds, and cancels it if the user moves focus elsewhere or the target disconnects. Controlled EN/FR tests cover this timing, and a real minimal READY/identity journey confirms return to the same button with no automatic operation retry. This change was initially prompted by a misclassified browser failure; that diagnosis is corrected below. The full journey had not actually reached identity verification.

## Operating guidance

Open `/{locale}/dashboard/finance/cash-command` and `/{locale}/dashboard/accounting/close`, with `en` or `fr` and an authorized tenant user. After a posted count, refresh the affected period: Close should show that evidence requires review. Resolve actual obligations, run a fresh assessment, and have a separately authorized certifier deliberately export a current certified pack. Refresh Cash to see the current period result. Opening a retained invalidated run should still show blocked evidence; that history is not a current certificate.

If Cash remains blocked, inspect its listed conditions. A newer successful assessment is insufficient when there are unresolved historical findings, missing evidence, another unreviewed period or ambiguous latest assessments. Repeated count submissions reuse their recorded result. A failure to retain invalidation must roll back the count transaction; do not edit a status to simulate success. Outbox PENDING proves enqueue, not delivery.
