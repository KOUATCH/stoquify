# Independent source-decision withdrawal

PR-10 remains **In progress**. This milestone closes the missing correction path for an approved nonfinancial corroborating-source investigation, including a run subsequently signed. It does not complete the entire sign-off workflow or provide generic incorporation of sources first arriving after signature.

## Bounded acceptance contract

- An authorized operator can review and propose withdrawal of the exact retained nonfinancial approval.
- The proposal and rejection leave the effective approval and signature in place.
- Approval requires fresh authentication, current tenant authority and a reviewer other than the proposer, original source makers/recovery actor, prior approval actor and current signer.
- The retained approval, proposal lineage, terminal exception/item hashes, signing audit and certificate hash must verify. Current source disagreement does not prevent withdrawal; new approval must validate current evidence again.
- Approval atomically reopens the exception and investigation, returns the run to NEEDS_REVIEW, retains its old certificate in the withdrawal receipt, clears the active signature and invalidates affected close evidence. Payments, matches, allocations and journals are unchanged.
- Stale revisions, competing updates, duplicate requests and failed audit writes cannot produce partial or repeated effects. Exact withdrawal retry never reopens a later reapproved/signed run.
- The existing EN/FR exception panel must explain consequences, preserve the request across authentication/reload, distinguish withdrawal history from closure history and support keyboard/reflow.

## Delivered behavior and source boundaries

`payment-source-decision-withdrawal.ts` validates the historical approval separately from today's corroboration. It permits only retained, resolved, unposted source investigations. It rejects financial cases, prior posting history, tampered terminal records, broken lineage/audits and inconsistent signature state. It returns a revision and explicit reviewer exclusions.

The existing closure contracts accept the optional `REOPEN_SOURCE` purpose for preview/proposal. The decision derives purpose from the stored proposal. Existing protected actions retain tenant identity, module enforcement, permission and fresh-authentication checks. Services retain active actor and accounting-read checks, open-period control, Serializable transactions and conditional exception/item/run writes. No database migration is required.

Approval receipts retain the earlier source approval reference, before-investigation record, before-exception record and full prior certificate. The current pointers are cleared and the latest withdrawal reference retained. Reapproval produces a fresh source decision and requires preparation/signing again. The source manifest consumes only the new verified decision.

The real reapproval test exposed a second-signature defect: the signing event key identified only the run. A later valid signature collided with the original payload. New signature event keys now include the certificate hash. Existing signed-state retries still return the retained signature; old events are preserved. The notification worker verifies each retained signature event/audit and deduplicates each event separately.

The existing exception panel uses the established dashboard surface, attention border, focus treatment and buttons. Resolved source cases offer **Review withdrawal**. Their preview names the earlier decision and retained certificate. Pending requests preserve the withdrawal operation, and history labels distinguish withdrawal proposal, rejection and approval. Back navigation now focuses the remounted Open case button; a real focused browser check reproduced the earlier fallback to the list container. Selection is not represented as approval.

## User and operator procedure

Open `/en/dashboard/finance/reconciliation` or `/fr/dashboard/finance/reconciliation`, open exception decisions, choose all cases, then inspect the resolved source investigation.

1. Enter why the earlier interpretation needs withdrawal. Obtain the discrepancy from the provider statement/callback, payment reference or investigation findings. The application supplies the existing decision ID and certificate hash; do not invent or manually replace them.
2. Select **Review withdrawal**, check the retained decision/certificate and consequences, then propose withdrawal. Complete password reauthentication if requested and retry the retained request. A proposal does not withdraw approval.
3. An eligible independent reviewer opens the proposal, examines the reason and retained evidence, enters a decision reason and approves withdrawal or rejects it. The organization administrator supplies the required reconciliation-read, exception-resolution and accounting-read permissions. The organization must provide an eligible reviewer; the system cannot manufacture independence.
4. On approval, the investigation is reopened and the run needs review. Investigate/correct the underlying source through its owning workflow. Then use normal independent source approval, preparation and signing. A withdrawal does not assert that the earlier match or payment is wrong and does not create a journal reversal.
5. For response loss, use the retained request's retry. For a changed review, refresh, inspect current history and create a new proposal. An old approved withdrawal retry only returns its original receipt.

A closed accounting period still requires the established period workflow; this implementation does not bypass it. Earlier certificate bytes remain in controlled receipt evidence. This change does not add a new public historical-certificate download endpoint.
