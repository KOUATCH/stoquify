## Implementation decisions from the current trace

The only production caller is SalesClientPage through the sales-component re-export. The old component initializes a new Date on every render, uses the literal default-location when no location is supplied, and swallows a failed action while rendering Loading/No sales and zero-valued cash. Both the component and service contain synthetic session identity; the component also contains fixed goal and satisfaction values. The fallback uses openingBalance 200. These defects are independent of external product approvals.

The stored DailySalesReport.date is PostgreSQL DATE. Its lookup must use the selected calendar date, while timestamped orders need inclusive-start/exclusive-end boundaries in Organization.timezone. A failed or ambiguous timezone conversion must be explained, not silently interpreted in the server timezone. Existing inventory history implements this distinction privately; analytical-context-contracts validates source currency/timezone/period metadata and should be reused where practical. Tests must include Douala and Paris 23/25-hour days, invalid dates/timezones, and organization-local today.

The fallback's order statuses include CONFIRMED, PROCESSING, SHIPPED, DELIVERED and COMPLETED. Its value is therefore confirmed-order value, not posted revenue or completed payment count. Cash/session/targets cannot be derived from those orders. The shared getSalesOrders helper also supports the older financial metrics model; changing it globally would expand this correction. Prefer a dedicated daily-report read owner with typed serializable contracts, keeping the other metrics implementation stable and recording its unsupported estimates for the reporting review.

The existing fallback payment relation filters deletedAt only, includes every status and combines credit with digital payments. It cannot be labeled today's collected cash. Payment semantics and refund producers are being traced separately. Until evidence supports a specific collection read model, remove unsupported cash/session conclusions rather than display zero or invent a status. A stored report can expose its recorded cash fields with a saved-report source label; an expected drawer balance must not be computed from an unverified formula.

Location choices must come from same-tenant report metadata and include explicitly retained locations needed for historical reads. A missing supplied location is a scope error. No locations is a distinct setup state. The default is a real configured location selected deterministically, never a fabricated ID. Reading report location names must not accidentally add a new locations.read permission requirement. Current route sales.read and action reports.read requirements need coherent localized denial while preserving both established authorities.

The client should key data by current user, organization, selected calendar date and location. Ignore delayed responses after a key change, hide prior-tenant data immediately, retain scope inputs on failures and offer an explicit refresh. The service's generated time and saved-report generation time are separate; a completed fetch is not a real-time feed. Currency comes from the organization with sufficient displayed precision, not a dollar prefix. Use neutral/informational tokens for scope and source, not success styling to imply healthy operations.

At this checkpoint these remain planned changes. No sales application source or test has been changed while the combined build runs.
