# Role assignment authority — bounded correction in progress

Evidence date: 2026-09-06. Baseline: source v22 for the preceding profile checkpoint; the role helper/tests changed afterward and require the next source checkpoint. This is OA-ROLE-CREATE/UPDATE work, not a complete role-governance workflow.

Source trace: `actions/roles/createRole.ts` and `updateRole.ts` call `role-auth.ts#assertCanAssignPermissions`, then `services/roles/role.service.ts`. Update with `permissions: []` reaches the helper because an empty array is truthy. The helper previously returned on zero length, so an actor with `roles.update` but without `roles.permissions.assign` could clear all permissions. It also returned for `ctx.isSuperUser`; the current RBAC context derives that flag from tenant wildcard permission. That skipped the canonical risk-aware checks and allowed a wildcard actor to grant a critical permission they did not explicitly hold.

Focused action reproduction failed two intended denials: both returned success and reached the role service. The test receipt is `../../evidence/role-assignment-authority-before.json` (2 failed, 9 passed; tool chunk fdc4c0). No real role was changed.

Correction: only omitted/null permission input skips assignment checks. An explicit empty selection still requires permission-assignment authority. Tenant wildcard status no longer bypasses the existing canonical permission/risk checks. Metadata-only edits continue through their existing `roles.update` path. An explicitly authorized empty selection is passed unchanged to the owner service. This shared helper also applies to role creation; an explicit empty initial permission selection now requires assignment authority.

After correction, the action suite plus existing role-service and invitation grant-policy suites passed 24 tests across three suites (`../../evidence/role-assignment-authority-after.json`, tool chunk 630c1a). The correction does not change the canonical permission list or grant risky permissions to any actor.

Remaining engineering work: move authoritative role-change validation and commit-time permission/session checks into the service; add a mandatory same-transaction audit, stale/concurrent edit protection, safe recovery and last-administrator availability protection. Current role service still updates and reloads outside a transaction and uses best-effort security audit after commit. Role form/read errors, bilingual navigation, current grantable options, reader/editor affordances, retained history and actual EN/FR browser/database verification remain open. Do not treat this helper correction as role-workflow completion or professional IAM certification.

Further current-source dependencies: `config/permissions.ts` defines both `roles.permissions.assign` and `roles.permissions.remove`; the current role helper only checks assignment, so complete delta-based grant/removal governance is still needed. `RoleForm` submits its full permission list for a metadata edit, renders the legacy catalogue and unlabeled group checkboxes, and navigates with untranslated `/roles` links. The role update page discards failure codes and turns any failed read into NotFound. Member deactivation lives in `services/users/user-lifecycle.service.ts`: it prevents self-deactivation and persists a mandatory audit, but does not recheck current actor authority under locks, revoke sessions explicitly or protect the last remaining administrator. It also cancels pending invitations by status without the newer invitation-management event/outbox contract. Coordinate these boundaries when implementing full role and member lifecycle controls; separate helper tests do not prove them.

The additional-organization handoff was also revalidated: `createOrganizationForSettings` creates an organization and administrator role but no owner/member account, while `User.organizationId` is required and single-valued and email is globally unique. The management table's success message cannot establish a usable second workspace. That workflow needs a coherent supported owner/access handoff; do not broaden tenant directory access or move existing user records across tenants as a shortcut.
