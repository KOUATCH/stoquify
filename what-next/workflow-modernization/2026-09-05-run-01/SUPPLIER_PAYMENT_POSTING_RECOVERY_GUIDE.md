# Recover supplier payment posting

This procedure repairs accounting for a supplier payment already recorded as executed. It does not send money, change the payment amount or establish bank settlement. The original payment, allocations and supplier ledger credit remain intact.

## Open and select

Open `/en/dashboard/purchases/payables/payments/record` or the corresponding `/fr/` route. Choose **Recover payment posting** / **Reprendre la comptabilisation des paiements**. The recovery route is `/[locale]/dashboard/purchases/payables/payments/recovery`.

Search for the existing payment number or supplier. A failed posting offers a review action. A completed recovery offers retained history. The user must currently hold `purchasing.ap.payment.release` in the same organization and must differ from the original requester and approver. The original independent execution recorder may perform recovery. An administrator must review and grant authority through normal access management; entering another actor ID cannot provide it.

## Inputs and where they come from

| Information | Responsible person and source | What to do |
| --- | --- | --- |
| Existing payment | AP operator; retained payment number and supplier in the payment screen | Select the recorded payment. Do not create another payment to repair its journal. |
| Request, approval and execution evidence | System records from the preceding request, approval and execution workflow | The server verifies these records. No new amount, date, destination, approval or execution claim is entered here. Missing legacy evidence requires separate review. |
| Accounting period | Accountant; the period covering the original payment date | It must be the original batch period and the only covering open period. Follow the existing period controls; this screen cannot reopen a period. |
| Posting rule and accounts | Accountant; the organization's reviewed supplier-payment posting configuration | Correct missing or invalid rules/accounts through existing accounting administration. Use organization-approved accounts, not example fixture codes. |
| Bank or cash journal | Accountant; current journal configuration | Exactly one active default journal of the required type must be available. |
| Currency and country setup | Accountant/configuration owner; original payment currency and organization country setup | Resolve the displayed mismatch or missing setup using reviewed configuration. Prototype acceptance is not country or statutory approval. |
| Password | The signed-in operator's own current account credentials | Verify it when requested. Never share it in a report, screenshot or evidence document. |
| Confirmation reference | Generated by the application from the reviewed configuration | The application retains this exact reference for an interrupted submission. Do not invent or replace it when the outcome is unknown. |

## Review, confirm and recover

1. Review the payment amount, execution reference, original date, period, rule and journal. Text explains missing setup or incompatible reconciliation work. Unresolved conditions prevent confirmation.
2. After correcting setup, obtain a new preview. Any configuration change after the preview requires another review; a stale confirmation does not post.
3. Confirm using the requested password assurance. The existing accounting kernel posts against the retained batch in one database transaction. The recorded payment is not repeated.
4. If the response is interrupted, reload the same browser session and choose **Retry** with the retained confirmation reference. Password verification is requested again. Do not clear browser session storage while the result is unknown; ask an authorized operator to inspect retained history first if that storage was lost.
5. Inspect both the recorded posting outcome and current reconciliation state. Successful recovery resolves the original posting-blocker exception while retaining its evidence, then opens a separate missing-statement obligation. Continue bank-statement matching in the reconciliation workflow.

History verifies the original execution link, recovery event, journal and source link. Changed or incomplete evidence produces a review requirement rather than a successful empty result. Existing matching, settlement or suspense-allocation work prevents automatic recovery and needs accounting/reconciliation review.

## Rollout and operational recovery

No schema migration is required. The implementation reuses existing payment, posting batch, journal, reconciliation exception, business-event and audit records. Deploy the service, action, route and both translation namespaces together only through the normal release process. No production deployment was performed for this checkpoint.

Begin with an authorized test cohort and an eligible failed posting. Compare invoice amount paid, supplier balance, allocations and supplier ledger entries before and after; they must remain unchanged. Expect one journal for the retained payment batch, one existing reconciliation transaction and one applied recovery event. Investigate a review-required result, repeated stale configuration, transaction failure or missing retained evidence before proceeding.

For an application rollback, withdraw access to the recovery entry point through an authorized release change. Preserve all committed records and audit events. Do not delete the journal, reset the payment or reopen resolved exceptions to undo recovery. A financially incorrect journal needs the existing authorized correction/reversal process, which remains a separate workflow under review.

## Verification limits

See `PAYMENT_POSTING_RECOVERY_VERIFICATION_V83.md` and `evidence/payment-posting-recovery-v83.json` for exact tested source and results. Synthetic localhost fixtures do not establish bank execution, evidence authenticity, statutory compliance or production readiness. Full payment reversal, late/changed-date execution, legacy evidence adoption, final credit-aware invoice status and downstream close remain unfinished engineering work.
