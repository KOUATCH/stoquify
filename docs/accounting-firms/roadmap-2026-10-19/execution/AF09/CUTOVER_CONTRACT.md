# AF09: staged opening position contract

**Version:** opening-position-v1 / opening-controls-v1 / opening-preview-v1. **Date:** 20 October 2026. This is a bounded technical preview contract, not statutory certification or permission to apply balances.

## Pilot and source of truth

The selected synthetic pilot is Cameroon (`CM`), XAF, with cutover at **1 October 2026 00:00 Africa/Douala**, represented as `2026-09-30T23:00:00.000Z`. The client organization must currently have country `CM` and currency `XAF`. No conversion or other cutover date is supported.

The source position and independent controls are two separately uploaded JSON documents. Each carries an `evidenceReference`. The test controls are independently authored literals, not totals generated by the preview algorithm. This proves that the implementation compares independent inputs; it cannot prove the provenance or independence of arbitrary user-supplied files. An accountant remains responsible for obtaining reliable external controls.

The production contracts are [opening-position.contract.ts](../../../../../services/onboarding/opening-position.contract.ts). Complete synthetic examples are [source](2026-10-20-run-01/source.json) and [controls](2026-10-20-run-01/controls.json). Unknown object fields are rejected.

## Input records

| Document / section | Required fields and meaning |
|---|---|
| Source header | `version=opening-position-v1`, `country=CM`, `currency=XAF`, `cutoverDate=2026-10-01`, `timezone=Africa/Douala`, `evidenceReference` |
| `stock[]` | `sourceId`, source keys `item`, `location`, `account`, exact `unit`, and decimal strings `quantity`, `unitCost`, `value` |
| `openItems[]` | `sourceId`, `kind=AR|AP`, source `counterparty`, `document`, `account`, `sourceDate`, `dueDate`, `currency`, decimal strings `original`, `settled`, `outstanding` |
| `ledger[]` | `sourceId`, source `account`, `domain=AR|AP|STOCK|CASH|EQUITY`, `side=DEBIT|CREDIT`, decimal string `amount`, `currency`, and `covers[]` containing source detail IDs |
| Controls header | `version=opening-controls-v1`, `evidenceReference`, matching fixed country/currency/cutover date |
| Controls totals | Decimal strings `stock`, `ar`, `ap`, `debit`, `credit`; `quantities[]` containing `unit`, decimal-string `quantity` |
| Mappings | Five arrays: `accounts`, `customers`, `suppliers`, `items`, `locations`. Every entry has `source` and `targetId`; targets must be current active, nondeleted client records |

Limits: 100 combined source rows, 100,000 UTF-8 bytes per document, 200 active selector records per category and 100 retained revisions per client/cutover. Oversized catalogs are rejected rather than silently truncated. The UI supplies JSON field guidance and retains source mappings for revision. It is a technical pilot upload, not an arbitrary spreadsheet importer.

## Calculation and tie-out

Money accepts nonnegative decimal strings with at most twelve whole digits and two decimal places; quantity accepts twelve whole digits and three places. Integer-scaled `BigInt` arithmetic avoids binary floating-point rounding. Quantity times unit cost is rounded half-up to two places per stock row. These are the repository-aligned technical precision rules for this pilot; no currency/legal policy expansion is claimed.

AR/AP outstanding must be positive and equal original less settled. Source dates must be actual ISO calendar dates before cutover; due date must be valid and no earlier than source date. Stock quantity must be positive, match the mapped item's active tenant unit, and multiply to the supplied value. Duplicate source IDs, stock positions, counterparty documents, mappings or ledger accounts produce explicit issues.

AR, stock and cash require debit-side asset accounts; AP requires credit-side liability accounts; equity requires credit-side equity accounts. Every AR/AP/stock detail must be covered exactly once by the matching ledger domain/account, and its amount must agree with that ledger control. Cash/equity cannot cover subledger details. Total ledger debits must equal credits. Customer credits, supplier debit balances, negative stock, historical transaction recreation and mixed currency are outside this bounded pilot.

The manifest compares stock value, AR, AP, debit, credit and each unit's quantity against the separately supplied controls. It reports proposal, control and signed difference. Invalid or unsupported-currency amounts are unavailable, not zero; incompatible details are not displayed as XAF amounts. Numeric differences and mapping issues remain visible. Positive preview review requires zero issues.

The balanced fixture has stock 25.00 XAF (2.500 kg at 10.00), AR 100.00, AP 50.00, cash 25.00 and equity 100.00. Debits and credits are both 150.00. The mismatched control fixture uses AR 99.00, producing a visible +1.00 difference.

## Provenance and states

Each `FinancialOpeningRevision` retains exact uploaded text, filenames, source/control SHA-256 hashes, mapping hash, semantic dataset hash, canonical proposed manifest/digest, creator, timestamps and review evidence. The digest includes the selected current master-record evidence. A PostgreSQL trigger rejects deletion and alteration of retained source, mappings or manifest, and makes completed review decisions immutable.

| State / operation | Behavior |
|---|---|
| Stage | New immutable revision and audit, bound to expected latest revision |
| Exact command retry | Same actor/input/idempotency key returns the original receipt |
| Same semantic dataset | Detected despite JSON whitespace changes; no extra revision if selected masters are unchanged |
| Changed file / mapping | New revision supersedes prior review; prior evidence stays retained |
| Changed mapped master | Current digest differs; visible `STALE`, review disabled until a fresh revision |
| Independent review | Different actor, current authorization, fresh authentication and exact latest digest required |
| Positive review | `REVIEWED` means the preview was reviewed; `canApply` remains false |
| Corrections | Independent reviewer may record `CHANGES_REQUESTED` for a mismatched staged preview |
| Previous revision | Cannot be reviewed after a newer revision exists; old decisions are not reactivated by duplicate upload |

## Authorization, concurrency and privacy

AF09 reuses AF08's current workpaper authority wrapper over AF04 engagement enforcement and the existing named-client consent. Firm assignment alone grants nothing. Read requires Close read access, stage uses the existing comment/preparation capability, and review uses accountant review plus fresh authentication. Home accounting and target Close module checks apply. A Close assessment or period is not required merely to inspect an opening position.

Transactions lock current authority first, then a client/cutover advisory lock, then selected master rows in deterministic order. Source/command version checks and final authorization revalidation occur inside the transaction. Audit failure rolls back staging. No network provider work occurs in these transactions. The configured transaction limit is 20 seconds with a 10-second acquisition wait.

The bilingual route is `/[locale]/dashboard/accounting/opening-position?clientOrganizationId=...`, linked from the existing firm portfolio. IDs supplied in navigation are context only; the service reauthorizes. Denial clears the visible preview. Scope changes and hidden-tab events invalidate late responses and clear uploaded documents, conclusions, password and pending commands. Uncertain submissions offer explicit retry of the same saved command. Fresh authentication does not silently resubmit.

Source files and conclusions contain sensitive client information; they are retained in the client-scoped evidence table and are not publicly exported by AF09. The immutable retention policy also prevents cascaded client deletion while evidence remains. A governed retention/legal deletion policy must be agreed before production activation.

## Financial boundary and recovery

Staging/review writes only `financial_opening_revisions` and audit logs. It does not invoke journals, inventory, AR, AP, master import, external delivery, or business-event posting. Existing master-import financial restrictions and opening-readiness blockers are unchanged.

Rollback means disabling the new route/actions and retaining the additive table and evidence. Do not drop retained revisions or reverse financial records: AF09 creates none. Retry ambiguity is resolved by the saved idempotency key and refresh. Correct source errors through a fresh revision. The [domain write plan](DOMAIN_WRITE_PLAN.md) specifies the separately gated AF10 work.
