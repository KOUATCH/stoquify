# S08/S09 execution and verification

Started 15 October 2026; final verification continued 16 October 2026. Scope: the initial POS/AP operator cohort and one POS maintainability extraction. No production access, deployment, application migration, dependency installation, staging or commit was performed by this task.

## Changes and evidence

### S08 — operator recovery and truthful outcomes

Three demonstrated gaps were corrected:

1. AP execution confirmation removes its review button. Closing the result dialog previously left keyboard focus on `BODY`. The workbench now returns focus to a connected, enabled invoking control, or its stable page heading when that control disappeared. Resuming a pending recording also remembers its invoking control.
2. A successful, identity-bound AP response could be followed by a session-storage cleanup exception. The outer catch then displayed “outcome could not be confirmed” alongside the confirmed result. Cleanup now has its own EN/FR message. It does not downgrade known business truth or generate a new retry identifier. If storage remains unavailable, the original retained reference may reappear after reload; the message explains this.
3. Acknowledging a recovered POS sale removes the focused recovery button. A real Chromium probe recorded `{ "tag": "BODY", "testId": null }`. Successful cleanup now returns focus to the existing checkout footer. Failed cleanup retains the recovery controls and their warning instead.

The existing page contracts, UI primitives, tokens, server authority checks and financial commands remain in place. No timestamp, URI or evidence-hash input was removed based on an assumed operator preference. No measured productivity improvement is claimed.

The AP regression run before correction had **9 passing and 2 failing tests**, reproducing focus loss and the contradictory unknown-outcome message. Both now pass. The POS focus baseline is retained separately in `pos-focus-before.json`.

### S09 — one pure result projection

`services/pos/commit-result.ts` now owns the initial commit-result contract, schema-version constant and pure projection. `pos.service.ts` calls it at the same point inside the existing financial transaction, before envelope hashing and durable registry transition. The public `commitPOSSale` entry point and its exported result type remain compatible through a type re-export.

The extraction preserves field order and values, decimal conversions, explicit nulls, journal order and provisional receipt/fiscalization state. It does not move permission checks, transaction boundaries, event creation, retries, idempotency checks, receipt completion or hash calculation.

Selection evidence: `git log -G 'resultSchemaVersion|receiptStatus|callerReplayed' -- services/pos/pos.service.ts` identified changes in commits `62a56036`, `7736416b` and `35b4cc6a`. S04/S05 also found a real receipt-completion replay race in this service. The extracted module has one runtime dependency, the existing pure money helpers; receipt types are erased imports. A reviewer can now inspect result disclosure and provisional-state semantics without loading the database/action dependency graph. This is a bounded reviewability improvement, not proof of reduced team lead time or permission for further decomposition.

### Browser fixture contract

`scripts/verify-s08-s09-browser.cjs` builds a separate Next fixture under `.codex-tmp/`, whitelists its child environment, binds to `127.0.0.1` and blocks external browser requests. It imports the actual operator components and global styles. Explicit TypeScript/webpack aliases replace actions, permissions, query hooks and checkout lifecycle with deterministic browser adapters. Offline sync and receipt-token panels are outside this cohort and are stubbed. No application layout, middleware, real session, database or provider is imported into the fixture. The fixture build skips automatic type/lint checks; those are run separately.

Coverage matrix: EN/FR × 1280×900 and 390×900. AP scenarios: confirmed execution with failed ledger posting and reconciliation suspense, lost reply/reload/same-command retry, stale revision, denied review with private state cleared, failed queue read, and storage cleanup failure after confirmed execution. POS scenarios: uncertain commit followed by reload and recorded-result acknowledgement, stale retained cart requiring explicit review, and denied commit without success notification. Critical action buttons are reached through Tab/Enter; form values use Playwright input filling. This is keyboard-navigation evidence, not a claim that every input was entered through a keyboard-only script or that a screen reader audit passed.

The final run records URL, synthetic role, locale, viewport, exact adapter calls, screenshots and Playwright traces per scenario. Assertions cover no duplicate POS commit during recovery, exact AP retry-command reuse, no false success, visible status distinctions, focus restoration and no horizontal page overflow. No actual bank/payment provider, full application login, tenant switching, long-queue performance or real operator task-time measurement is represented by these adapters.

Final browser result: `final-2026-10-16/browser.json`, with 36 PNGs and 36 traces. All 12 AP completed/retried/cleanup-failure result closures returned focus to the stable heading; all four POS recorded-recovery acknowledgements returned focus to checkout. No scenario reported a page error. The isolated production fixture build passed. Selected narrow EN/FR captures were visually inspected; this does not constitute an accessibility conformance audit.

The earlier broad browser baseline and first after-build were interrupted; their partial artifacts are diagnostic evidence only. The separately recorded failing regression tests and POS Chromium focus probe establish the before behavior. The initial fixture resolver problem was corrected before browser verification and is not an application defect.

Installed verification versions: Next 15.5.27, React 19.2.6, Jest 30.4.2, TypeScript 5.8.3, Playwright 1.61.1 and Prisma Client 6.19.3. The browser matrix uses installed Chromium only. Fixture role names describe the adapter's identity, not a successful real-session login. POS starts with an existing synthetic cart; product entry/catalog and the application navigation shell are outside this fixture's claim.
