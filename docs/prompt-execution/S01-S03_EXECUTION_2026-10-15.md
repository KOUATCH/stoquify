## Logging contract

The default sink writes one JSON record using the matching console level. `setLoggerSink()` restores that default. Context is bounded, uses the existing secret-redaction policy, removes common personal-data keys/email strings, and retains only raw error class/code, not SQL, stack, cause or error message. Do not use arbitrary business payloads as log context; redaction is a secondary control.

Synchronous sink errors and rejected promises fall back to console with `logSinkFailed: true`. If console itself fails, logging stays best effort and does not throw into the transaction. No paid transport or background infrastructure was added. The local smoke artifact proves actual process-console emission and redaction, not hosted ingestion.

`protect` now carries its correlation ID into handler context and logs permission/fresh-auth denials. The same ID appears in the safe failure response. Audit storage success stays unchanged except for optional explicit correlation in `changes`; organization-less events and storage failures emit safe operational records. Payroll failure logs occur outside the rolled-back transaction and are not evidence of a committed settlement.

## Payroll authority and concurrency contract

1. The browser action supplies session ID/token from server-verified fresh-auth claims. Client-provided identity, authority and time cannot replace these values.
2. Each Serializable attempt acquires organization/configuration/grant, actor, tenant-owned role/membership and session locks. Persisted permissions, account usability and exact session ownership/token/expiry determine access. Caller permission arrays and module decisions no longer authorize settlement.
3. A revocation that commits before admission denies the operation, including after a serialization retry. A revocation trying to modify authority already held by settlement waits until that transaction completes. This is an explicit ordering policy, not a promise to cancel a previously admitted transaction instantaneously.
4. New settlement writes require current write entitlement and password assurance for the same organization, level at least one, no active assurance lock and age at most 300 seconds. Authority time is recomputed after lock waits and again after economic writes, before returning to commit. Expiry at the final check rolls back payment, batch, business event, outbox, close invalidations and transactional audit together.
5. Service-level replay requires current session, account, tenant permission and **read** entitlement. It does not require new step-up because no new settlement occurs. The existing browser action remains stricter and requests fresh authentication/write access. Session credentials, correlation, caller timestamps and permission snapshots are excluded from command identity; a renewed session can recover the same recorded result.
6. P2034 and raw PostgreSQL serialization/deadlock errors (40001/40P01 through P2010) retry the complete transaction at most three times. Every attempt repeats authority checks. A caller-provided transaction must itself be Serializable.
7. Existing stored proof selection, balance revision, separation of duties, event identity and close invalidation remain in the transaction. No schema migration was added.

The provider bridge and inbox worker forward optional session identity to the same service boundary. A lease and supplied permissions cannot substitute for persisted authority. Missing/stale sessions fail closed through the existing failure/retry path. Source inspection found no non-test invocation of the inbox worker in app/actions/scripts/services. Do not persist user session tokens in queue payloads; unattended settlement needs a separately designed machine/delegation authority contract, outside these three steps. No automation bypass was introduced.

Repeated authority queries intentionally favor clear transactional enforcement. Their latency on the deployed database has not been measured; preserve the safety checks when profiling this boundary.
