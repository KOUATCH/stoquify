## S06: traffic-abuse boundary

Observed in the current middleware: an unbounded Map retained one entry per forwarded address, expired entries were never removed unless that same identity returned, denial had no Retry-After, and forwarding headers were accepted without an ingress trust contract. Historical backlog 002 describes an Upstash implementation, but the current middleware neither imports it nor shares state. Redis packages in a manifest do not establish a working Edge-compatible service.

Changes:

- The fallback retains at most 10,000 address buckets plus one overflow bucket. Requests reclaim expired buckets; no background timer is required. With no requests, retained memory remains bounded. Live entries are never evicted to admit new identities. New identities share the overflow quota while capacity is exhausted.
- The existing 200 requests/minute allowance and auth/static exemptions remain. Rate denials carry Retry-After and no-store; private receipt and statement policies remain intact.
- Address inputs have bounded length, IPv4 validation and canonical IPv6 representation. `STOQUIFY_TRAFFIC_IP_HEADER=x-real-ip` or `cf-connecting-ip` selects exactly one ingress-owned header, with no fallback to caller-forwarded headers if it is missing or malformed. Invalid configured names map to the unknown bucket.
- **Unset configuration preserves the untrusted forwarding-header partition for compatibility. It is spoofable and is not an authenticated client identity.** Do not enable the trusted-header option until the final ingress overwrites the selected header, strips caller values, and direct origin access is closed. Merely setting the variable does not authenticate a proxy.

This is a per-process fixed-window fallback, not distributed enforcement. Two processes have independent allowances. No shared client, shared outage policy or WAF rule was invented without a verified deployment. The fallback continues independently if a separately operated edge control is unavailable; it cannot promise the edge's global quota.

Shared-NAT capacity: ten tills making twenty counted requests per minute use the full existing allowance; the next request is denied. This is a deterministic budget exercise, not a production traffic measurement. A real till's request rate and false-denial rate must be measured before changing thresholds or routing more traffic through a shared rule.

Required release proof: document proxy chain/origin isolation, demonstrate header spoof resistance at that ingress, exercise two actual application instances against the chosen shared control, test its outage behavior, and measure legitimate POS/NAT false throttles. Keep this step open until that proof exists.

## S07: strict script CSP pilot

Current-source inventory:

| Producer / resource | Evidence and treatment |
| --- | --- |
| Next framework and streamed React scripts | Installed Next 15.5.18 `app-render.js` reads request CSP and extracts its script nonce. The pilot supplies a newly generated 144-bit nonce per request. |
| Theme bootstrap | `next-themes` accepts a nonce. Root layout forwards the middleware nonce through existing provider props. |
| UploadThing bootstrap | Installed `@uploadthing/react/next-ssr-plugin` emits inline JavaScript without a nonce prop. A small local bootstrap preserves its global config and server-inserted-script contract, adds the nonce and escapes `<` in serialized config. |
| Other explicit script tags | Source search found no additional application `next/script` consumers; tests containing script text are not runtime producers. Third-party dependency behavior still needs full-app browser proof. |
| Images/media | Next config lists Flaticon, Unsplash, `14j7oh8kso.ufs.sh`, `utfs.io`, and placeholder images. Existing broad HTTPS/blob image policy is retained. |
| Styles/fonts/connections | Existing inline style allowance, Google font allowances and HTTPS/WSS connections are retained. This is a script-policy pilot, not a completed network-origin or style restriction. |

`STOQUIFY_CSP_MODE` accepts `report-only` or `enforce`; absent, `off`, or an unknown value leaves the existing response policy. The exact cohort is `/en/login` and `/fr/login`, with an optional trailing slash. It excludes login-v2, public discovery, POS, APIs and signed evidence pages. These login/locale layouts already force dynamic rendering. The pilot adds private/no-store responses to prevent nonce reuse through shared caches; it does not force public/static routes dynamic.

Middleware removes incoming nonce and CSP request headers before supplying its own. Next receives a nonce policy on the request. Browser verification exposed an additional framework interaction: Next 15.5.18 copies middleware response headers back onto renderer requests, so the baseline enforcing CSP replaced the request's nonce policy. Five streamed Next scripts lacked nonces in the report-only run. The failing browser evidence is retained in `bootstrap-report-only-before-fix.json`.

The correction adds the same nonce to report-only mode's baseline enforcing policy for Next's renderer, with explicit CSP3 `script-src-elem` and `script-src-attr` overrides preserving the baseline's permissive inline behavior. The separate report-only policy measures the proposed restriction. This compatibility adapter targets CSP3 browsers: older browsers that ignore those overrides may enforce nonce restrictions during report-only mode. Verify the supported browser cohort before activating it outside the local pilot. Enforcement mode has no permissive script overrides. Its production script policy contains neither unsafe-inline nor unsafe-eval; development retains eval for tooling. No report collector was introduced; local browser tests collect securitypolicyviolation events without transmitting URLs or evidence tokens to a third party.

Rollback: set `STOQUIFY_CSP_MODE=report-only` to stop pilot enforcement while observing violations, or unset/set `off` to restore the baseline response policy. No production variable was changed. Baseline headers and private evidence policies remain. Before expanding the cohort, verify real EN/FR authentication and client navigation, POS, uploads/evidence/media and essential public flows; capture unexpected violations, rendering latency and cache effects on the intended preview deployment.
