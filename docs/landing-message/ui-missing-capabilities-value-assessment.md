# Stoquify: five UI capabilities that would increase user value

Assessment date: 9 September 2026. Scope: the current, heavily modified local workspace; this is an assessment and proposal, not implementation or certification.

The strongest next addition is **cross-module business-record search**. Users can currently search navigation destinations, but the inspected shell cannot return an actual customer, item, or transaction. Four other priorities address work that gets lost between screens: failed communications, audit investigations, stalled reconciliation alerts, and requests for access.

Two recommended workflows were absent within the inspected scope. Three are partially implemented through narrower domain screens. Those existing screens are explicitly acknowledged below; “missing” refers to the remaining workflow, not the whole underlying feature. Benefits and priority judgments are hypotheses; no customer timing, adoption, support-volume, or ROI measurements were available.

These are relative implementation judgments, not schedules. The ranking weighs pain, frequency, consequence, breadth, existing support, and effort. Search ranks first because it helps frequent work across several roles and can begin as a bounded read-only feature. Delivery ranks second because failures interrupt customer communication and onboarding, while much of the source evidence already exists. Audit has high consequence but more episodic use. Reconciliation recovery is important for a narrower specialist group and needs careful worker controls. Access requests affect onboarding and role changes but require a new durable workflow and administrative ownership.

No observed usage data establishes that ordering. If operating evidence shows frequent stalled reconciliation alerts or disputed unauthorized changes, recommendations 4 or 3 should move ahead of search.

## 1. Business-record search across modules

**Current fact and gap.** [Navbar](<E:/ohada saas/Focused projects/stoquify/components/dashboard/Navbar.tsx:146>) builds its search results from flattened authorized sidebar destinations, filters destination labels, and limits the result to seven. [Sidebar search](<E:/ohada saas/Focused projects/stoquify/config/sidebar.ts:361>) also searches navigation text. The live `customer` query returned navigation actions, consistent with that implementation. No shared record-search route, action, hook, or component was found in the scoped searches.

**Users and task.** A Purchaser receives an order reference while working in inventory, or a Sales Manager receives a customer code during a call. Today they first locate a module and then use its local list or detail workflow. The proposed search would take the reference directly and return authorized records.

**Smallest useful UI.** Extend the current header search with clearly labeled “Pages” and “Records” groups. Start with customers, items, and purchase orders; show record type, recognizable name/reference, location where permitted, and status. Open the existing detail page. Provide keyboard navigation, an accessible result count, cancellation, and explicit loading/error/empty states. Add more domains only after the first scope is useful.

**Importance and value.** This reduces navigation work that contributes nothing to completing the underlying task. Before: remember the module, open it, set a local search, then choose a record. After: enter an identifier and open the matching record. Expected benefits are faster retrieval, fewer wrong-record selections, and easier learning for occasional users.

**Dependencies and boundaries.** [listCustomers](<E:/ohada saas/Focused projects/stoquify/services/customer/customer.service.ts:201>) already accepts bounded paging and search, scopes to an organization, and excludes deleted records. [Customer hooks](<E:/ohada saas/Focused projects/stoquify/hooks/useCustomerManagement.ts:120>) and [customer actions](<E:/ohada saas/Focused projects/stoquify/actions/customers/customer-management-actions.ts:94>) demonstrate existing domain entry points. They are foundations, not a ready universal search API. Add a server-owned aggregator and minimal result contracts; implement bounded item/order queries where needed. Resolve identity, tenant, location, permissions, and module entitlement before retrieving each domain. Do not download complete domain lists to the browser. Keep payroll, private HR data, and payment details outside the initial scope; counts and snippets must not reveal inaccessible records.

**Measurement.** Median time to open the correct record in representative retrieval tasks; proportion of searches that lead to the intended record. Establish a baseline with the current navigation before setting targets.

**Tradeoff and confidence.** Broad search improves convenience but expands the number of data boundaries touched by one request. A limited domain set and server-side limits keep the first release manageable. High confidence in the shell gap; broader absence is a scoped search conclusion.

## 2. Communication delivery exception inbox

**Current fact and gap.** [Notification settings copy](<E:/ohada saas/Focused projects/stoquify/app/[locale]/(dashboard)/dashboard/settings/notifications/NotificationsSettingsClient.tsx:64>) explicitly separates temporary notices from durable delivery. However, [customer statement history](<E:/ohada saas/Focused projects/stoquify/components/customers/CustomerStatementHistory.tsx:153>) already shows processing state and attempt counts, and [the statement workflow](<E:/ohada saas/Focused projects/stoquify/components/customers/CustomerStatementWorkflow.tsx:281>) contains recovery commands. [Invitation history](<E:/ohada saas/Focused projects/stoquify/components/Forms/users/InvitationHistory.tsx:51>) also displays delivery outcomes. The missing workflow is a cross-record queue that identifies which communications need attention without opening each source record.

**Users and task.** A Sales Manager wants to know which customers did not receive yesterday's statements; an Admin wants to identify deferred invitations before staff start work. A cashier may need to investigate a receipt send within their permitted location. Currently the operator must know which record to inspect.

**Smallest useful UI.** Add a persistent “Delivery issues” tab beside existing notification settings. Initially include supported statement, invitation, and receipt workflows with verified adapters. Filter by type, channel, date, location where relevant, and outcome. Each row shows a masked recipient, source reference, last attempt, a plain-language reason, and the next safe action. Open the existing source recovery workflow where available. Show “provider accepted” separately from recipient delivery or reading; an unknown result must remain unknown.

**Importance and value.** External communication is part of completing a business task. Before: a successful queue operation or a vanished notice can leave the operator unaware of a later failure. After: unresolved sends remain findable and actionable. Hypothesized benefits include fewer missed statements/invitations, fewer repeated sends, and shorter support investigations.

**Dependencies and boundaries.** [The receipt queue summary](<E:/ohada saas/Focused projects/stoquify/services/communication/whatsapp-receipt-worker.service.ts:393>) and [worker failure handling](<E:/ohada saas/Focused projects/stoquify/services/communication/whatsapp-receipt-worker.service.ts:86>) already expose deferred and failed work internally. [Invitation history data](<E:/ohada saas/Focused projects/stoquify/services/users/user-invitation-history.service.ts:71>) supplies attempts and recovery classification. Add a tenant-scoped, paginated read model normalizing source references and safe error codes. Reuse domain recovery services and their consent, freshness, version, and idempotency controls. New recovery commands are needed for types without an authorized operator path. A general notification-read permission must not grant access to all recipients or sensitive content. Persisted delivery evidence and supported provider configuration must be established per channel; adding a UI does not make an unavailable channel operational.

**Measurement.** Age of unresolved delivery exceptions; time from a confirmed failed/deferred outcome to an appropriate operator action. Track unknown outcomes separately.

**Tradeoff and confidence.** A shared queue reduces checking across screens but can leak contact details or encourage duplicate sending if it ignores domain rules. Prefer source-linked recovery initially. Medium–high confidence in the consolidation gap. Existing statement and invitation recovery are explicitly excluded from the missing claim.

## 3. Audit explorer across modules

**Current fact and gap.** [AuditLog](<E:/ohada saas/Focused projects/stoquify/prisma/schema.prisma:9261>) stores organization, entity, action, actor, changes, and time, with entity/time and organization/time indexes. [Accounting Control Center](<E:/ohada saas/Focused projects/stoquify/services/accounting/control-center.service.ts:387>) reads eight recent events for a restricted accounting/control subset. [Member history](<E:/ohada saas/Focused projects/stoquify/services/users/member-history.service.ts:17>) and [role history](<E:/ohada saas/Focused projects/stoquify/services/roles/role-editor.service.ts:17>) provide focused records. No general tenant audit screen supporting cross-entity investigation and filters was found. This is not a claim that audit trails are absent.

**Users and task.** An Owner or authorized Accountant investigates a disputed adjustment and asks whether a role change occurred shortly before it. An individual record history answers only part of that question.

**Smallest useful UI.** Add an “Activity & audit” destination under Settings for eligible readers, with date, actor, entity type/reference, and action filters. Show a readable timeline and a detail panel with available before/after fields, reason, and source link. Indicate absent fields explicitly. A later controlled export can reuse established export-safety patterns; it should not be required for the first useful viewer.

**Importance and value.** Users need understandable evidence for correcting mistakes, answering disputes, and exercising oversight. Before: combine limited domain histories and ask engineering for broader queries. After: follow the relevant sequence in one permission-filtered view. Expected impact is faster investigations and clearer accountability.

**Dependencies and boundaries.** Add a bounded audit-query service with a stable cursor, filter validation, entity-aware redaction, and source-link authorization. [Audit permissions](<E:/ohada saas/Focused projects/stoquify/lib/security/rbac-permissions.ts:267>) provides relevant vocabulary; [member-history authorization](<E:/ohada saas/Focused projects/stoquify/services/users/member-history.service.ts:39>) demonstrates fresh reader validation, while its export path applies additional controls. Audit-read authority should not automatically expose private HR changes, IP addresses, or every financial payload. Inventory event completeness and retention before offering “complete history”; the schema alone proves neither immutability nor comprehensive logging. Avoid reinterpreting financial events as ledger balances.

**Measurement.** Median time to answer a defined “who changed what?” investigation; share of those investigations requiring developer assistance.

**Tradeoff and confidence.** Broad visibility aids oversight but increases sensitive-data exposure. Start with a curated event taxonomy and safe fields. Medium–high confidence in the missing general explorer, with strong evidence that specialized audit views already exist.

## 4. Reconciliation alert recovery

**Current fact and gap.** [The durable reconciliation inbox](<E:/ohada saas/Focused projects/stoquify/components/finance/PaymentReconciliationWorkbench.tsx:1452>) already lists business alerts and scan state. It renders an alert as recorded, with type, date, severity, and amount when available. [Its query](<E:/ohada saas/Focused projects/stoquify/services/reconciliation/payment-reconciliation-dashboard.service.ts:356>) selects only certain reconciliation sources and the latest 25 records. [Its projection](<E:/ohada saas/Focused projects/stoquify/services/reconciliation/payment-reconciliation-dashboard.service.ts:425>) exposes notification payload status, not the complete processing-attempt history.

Meanwhile [PaymentReconciliationInboxItem](<E:/ohada saas/Focused projects/stoquify/prisma/schema.prisma:6130>) stores attempts, last error, next attempt, lease, and processed time. [Worker failure handling](<E:/ohada saas/Focused projects/stoquify/services/payments/payment-reconciliation-inbox-worker.service.ts:466>) schedules retries or moves exhausted work to dead letter. The missing interaction is inspection and controlled resolution of that processing failure. It is not a missing reconciliation workbench, business-alert inbox, or universal provider-health dashboard.

**Users and task.** An Accountant can see that a reconciliation alert was recorded but needs to know whether its processing has stalled and who can resolve it. An authorized Admin needs the safe failure reason and current state before intervening.

**Smallest useful UI.** Extend the existing reconciliation inbox with a “Processing issues” view. Show the last attempt, retry schedule, plain-language failure code, source reference, and last successful processing time. Offer a source link and an escalation/reference package first. Add a reviewed “Resume processing” command only for recoverable states once a dedicated service contract exists. The status of the financial obligation and the status of processing must remain separately labeled.

**Importance and value.** Merely recording an alert does not ensure it reaches the next operational step. Before: users see the business alert while troubleshooting requires worker inspection. After: they can recognize stalled processing, understand ownership, and initiate the correct recovery. Expected impact is shorter unresolved alert age and fewer support handoffs.

**Dependencies and boundaries.** Add a tenant-filtered read projection for processing evidence. Introduce a narrowly authorized recovery action; worker lease functions are not safe public UI commands. Require current state/revision checks, idempotency, audit, bounded retry, and protection against racing a live lease. Keep raw payloads, secrets, and lease tokens off the client. Existing worker tests describe retry, redaction, and ownership behavior at [the focused worker suite](<E:/ohada saas/Focused projects/stoquify/services/payments/__tests__/payment-reconciliation-inbox-worker.service.test.ts:116>); they were inspected, not executed. Preserve payment-reconciliation module checks and existing action permissions such as those in [reconciliation actions](<E:/ohada saas/Focused projects/stoquify/actions/payments/reconciliation.actions.ts:133>). This UI cannot certify provider uptime or settlement.

**Measurement.** Time a failed reconciliation alert remains without an owner/action; recurrence after an authorized recovery, with duplicate processing counted separately.

**Tradeoff and confidence.** Read-only diagnosis is relatively small; safe recovery is materially harder because duplicate or concurrent processing matters. Rank it below broader daily-work features unless measured failure incidence warrants promotion. High confidence in the contract gap, with no live worker outcome verification.

## 5. Trackable access requests

**Current fact and gap.** [The general denial screen](<E:/ohada saas/Focused projects/stoquify/components/NotAuthorized.tsx:9>) tells users to ask a workspace administrator, with navigation/sign-out recovery. [Settings route access](<E:/ohada saas/Focused projects/stoquify/app/[locale]/(dashboard)/dashboard/settings/settings-route-access.tsx:103>) distinguishes permission denial from module unavailability. [Entitlement decisions](<E:/ohada saas/Focused projects/stoquify/services/modules/module-entitlement.service.ts:332>) can be audited. No durable permission-request model, request action, requester status view, or corresponding admin inbox was found in the scoped search.

Module composition and change history already exist at [Settings / Modules](<E:/ohada saas/Focused projects/stoquify/app/[locale]/(dashboard)/dashboard/settings/modules/page.tsx:14>) and [its history tab](<E:/ohada saas/Focused projects/stoquify/components/modules/ModuleCompositionWorkbench.tsx:537>). Restricted functionality is not classified as missing; the missing capability is tracking a request to resolve a legitimate restriction.

**Users and task.** A Purchaser follows a link to an approval task and lacks its permission. They need to explain the business need, identify the responsible reviewer, and know whether the request was accepted or rejected.

**Smallest useful UI.** On eligible denial screens, offer “Request access” with a short business reason and a server-derived task/surface reference. Give the requester a persistent status and a link back to the original task. Add an admin review queue within Users & Roles, with decision reason and current authority context. Route module availability questions to the module administrator; do not offer a broad permission grant as the answer to every denial.

**Importance and value.** The current recovery depends on an untracked conversation outside the workflow. Before: repeat the problem to an administrator and chase the outcome. After: submit context once and follow a clear decision trail. Expected benefits are shorter legitimate access delays, less support repetition, and better-scoped grants.

**Dependencies and boundaries.** Add a durable, tenant-bound request lifecycle, deduplication, expiry/cancellation, and explicit requester/reviewer permissions. Review must call the existing role/member services and re-evaluate current grant authority. A request cannot create authority, approve itself, activate paid modules, or bypass fresh authentication and segregation rules. A status of “approved” must be distinct from “access applied” and confirmed access. Users should see only their own requests unless permitted to review others; denial responses must not reveal inaccessible record details.

**Measurement.** Median time from a valid access request to a recorded decision; repeated support contacts per request.

**Tradeoff and confidence.** Tracking improves accountability but can create administrative backlog. Define responsible reviewers and request expiry before introducing the queue. Medium–high confidence in the scoped absence; actual demand and denial frequency remain unmeasured.

## Architecture, controls, and product considerations

| Review lens | Assessment consequence |
| --- | --- |
| Platform, backend, and integration | Each domain retains its own rules; shared search and queues aggregate safe read models and link to authoritative domain commands. |
| Data, database, and migration | Use bounded queries, stable pagination, and evidence provenance. Access requests need a new durable lifecycle; none of the proposals authorizes a migration now. |
| Security, IAM, privacy, and fraud | Recheck tenant, location, role permissions, and entitlement on the server. Redact audit/delivery data. Keep recovery and access changes independently authorized and audited. |
| Frontend and design system | Extend existing shell, notification, reconciliation, and settings components. Avoid parallel dashboards for the same business task. |
| Workflow, accessibility, and localization | Design complete loading/empty/denied/stale/error states, keyboard navigation, announced outcomes, and English/French task language. These are proposed acceptance criteria, not an accessibility pass. |
| Product and business process | Validate the before/after examples with actual role users and baseline the metrics. The recommendation order is qualitative. |
| Quality and release assurance | Later implementation needs scoped cross-tenant, revocation, stale-state, failure, and browser checks proportional to its risk. This assessment ran no broad build or test suite. |
| SRE, performance, and cost | Bound search fan-out and polling. Preserve worker leases/backoff. Measure expensive audit queries before adding indexes or separate infrastructure. |
| SaaS packaging, growth, and customer success | Show features only for entitled domains; access requests do not grant subscriptions. Hypothesis: easier retrieval and visible delivery outcomes reduce support work. Pricing and willingness to pay are unmeasured. |
| Finance, reconciliation, audit, and records | Separate business state, processing state, and available evidence. Audit/UI summaries do not replace ledger or settlement truth. |
| OHADA/SYSCOHADA and country rules | Not applicable to changing statutory rules: none is proposed. These recommendations carry no legal, accounting, or tax certification. |
| HR/payroll, inventory/POS, and purchasing | Relevant only as scoped users/data sources; preserve sensitive HR boundaries, location scope, and domain workflows. No domain-engine change is proposed. |
| Offline/edge and AI/agents | Not applicable to new offline replay or model decisions: neither is proposed. Recovery remains explicit and service-governed. |
