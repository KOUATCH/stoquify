# Landing message implementation decisions

Date: 19 September 2026. Scope: public landing, login and registration in the current local workspace.

## Positioning

Primary audience: owners and managers of growing retail and distribution businesses in OHADA markets.

Central problem: sales, stock, purchasing and payment records become difficult to follow when teams work in separate tools.

Three practical benefits: review daily issues; follow stock and payment records back to their source; prepare accounting review from recorded operations. These require configured workflows, current data and appropriate access. No savings, compliance certification or automatic provider connection is promised.

Registration immediately records organization details and creates an unverified administrator account. The next step is email verification, followed by sign-in and configuration of locations, items, users and the enabled workflows. The canonical registration route does not create a default location unless one is requested. Payroll, statutory channels, provider connections and offline operation are conditional capabilities, not default activation promises.

## Content decisions

| Area | Decision | Reason |
| --- | --- | --- |
| Landing | Reduce twelve composed sections to six focused sections | One audience and a coherent path from outcome to setup |
| Hero | One primary registration action, one workflow action; labeled sample | The action should describe the page it opens |
| Benefits | Three everyday outcomes with setup conditions | Avoid a catalogue of overlapping technical promises |
| Workflow | Show a sale, stock movement, payment review and accounting handoff | Explain the connection with one concrete example |
| Product evidence | Retain the existing dated, redacted screenshot; remove decorative percentages | Historical product capture illustrates the interface but does not establish current live state |
| Adoption | Explain immediate account creation and later setup; preserve package details in a disclosure | No changes to commercial rules or module activation |
| Login | Center the existing form and remove the surrounding sales catalogue | Returning users need access and recovery |
| Registration | Keep all fields, consent, referrals and submission safeguards; shorten the introduction and name the next steps | Account creation is the start of setup |

## Boundaries

Existing working-tree changes are preserved. Authentication services, data schema, tenant controls, permissions, financial rules and deployment are outside the implementation write scope. Existing roadmap documents are proposals. Final verification and claims results are recorded separately after execution.
