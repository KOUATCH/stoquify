## Device, policy, signature and reference assumptions

- Enrollment binds organization, location, terminal and fingerprint. Public signing key, policy expiry and snapshot hashes are optional in the schema. Missing public key is surfaced as `LEGACY_UNVERIFIED`; no signature verification occurs in that branch ([signature check:203](../../../../services/pos/offline-sync.service.ts#L203)). No strict signed-device guarantee follows from enrollment alone.
- With an enrolled key, server crypto verifies the signature over the canonical entry hash. The entry hash binds device, sequence, event type, schema version, payload hash and previous hash. It does not itself bind every outer metadata/policy/time field. No browser key-generation/signing caller was discovered; queue input accepts an externally supplied signature. Enrollment/key lifecycle and a complete signed capture path remain prerequisites.
- Configured expiry is evaluated against server time at ingestion, not merely device capture time. Configured policy/source hashes must match or evidence is quarantined. Missing settings are not automatically denied. Reference freshness is **hash equality**, not a maximum age check; old `capturedAtDevice` with the same hash can enter PENDING_REPLAY. The new test characterizes this limit, not a policy recommendation.
- Captured offline receipts are provisional. Local payload checks reject caller-supplied final fiscal numbering. Ingestion acknowledgement and an internal sync certificate do not certify tax, payment settlement, legal delivery or OHADA compliance.
- Retained historical evidence must survive revocation/expiry. It must not be rewritten with a new device, operation ID, policy hash or timestamp simply to pass validation. Legitimate correction requires reviewed domain authority and an auditable process.

## Unsupported-state message and recovery path

Existing service restriction: “Offline POS capture and replay are disabled for the authorized development-only cash pilot.” Existing storage errors distinguish missing IndexedDB, unsupported strict transactions, blocked upgrade and quarantined evidence. Hook notifications say a manager must review conflicts. These messages exist in source; this run does not certify their delivery through the application UI.

Operator wording for the bounded runbook (not newly implemented UI copy):

> **EN:** Offline checkout is not available in this pilot. Keep this device's pending evidence. Reconnect and ask an authorized manager to check the original operation. Do not take a second payment or clear browser data to retry.
>
> **FR:** La vente hors ligne n'est pas disponible dans ce pilote. Conservez les éléments en attente sur cet appareil. Reconnectez-vous et demandez à un responsable autorisé de vérifier l'opération d'origine. N'encaissez pas un second paiement et n'effacez pas les données du navigateur pour réessayer.

1. Stop further offline capture on the affected device. Preserve the browser profile, queue identifiers, original payload/hashes and observed error; do not export secrets or customer data into general logs.
2. Reconnect using the original scope. Unknown transport outcomes remain unknown. After the existing lease expires, an approved integrated path may resend the identical original evidence; connectivity alone cannot confirm payment.
3. For revoked/expired/mismatched policy or reference evidence, have an authorized manager review server conflict history if ingestion reached the server. Record note and current revision. Review acknowledgement preserves the close blocker. Do not re-enroll or alter signed evidence merely to clear it.
4. The existing [recorded replay resolution service](../../../../services/pos/offline-resolution.service.ts) requires matching recorded sale/posting/replay proof. It is not a generic “discard failed queue” mechanism. A quarantined or never-ingested operation has no demonstrated self-service repair route in this envelope; preserve it for separately authorized engineering/domain investigation.
5. Keep unresolved items in shift/period readiness. [checkout-state.ts:28](../../../../services/pos/checkout-state.ts#L28) checks persisted pending/quarantined events and blocking certificates. This cannot discover local-only unsent queues. Integration of that evidence is an explicit future prerequisite, not assumed safe because the server count is zero.

Before enabling offline sales, complete P05's current DB/browser evidence, establish a supported client integration and signed device policy, and prove local-only pending visibility plus real replay effects. These are continuation conditions; P07 and later prompts were not run.
