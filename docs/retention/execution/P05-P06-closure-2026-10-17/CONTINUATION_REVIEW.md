# Review of initial browser attempts

The first actual application journey eventually reached the original retained request and submitted it with the keyboard. `BROWSER_RECOVERY.json` independently records the completed original sale before the browser response was suppressed. The whole-connection outage then exposed `Load failed` plus the misleading `Sale failed / Failed to fetch` notification. `BROWSER_RECOVERY_FINAL.png` and its body text were inspected. This is a failed pre-fix browser expectation, not a passing recovery run.

The first continuation used a body-wide UUID assertion. Review found that the synthetic cashier email shared the same UUID; therefore the loading screen incorrectly satisfied it. **All `INVALID_SELECTOR-*` artifacts are invalid for rendered-recovery claims regardless of their embedded PASS field.** Their database snapshots still record what was read, but no UI pass is counted from them.

The corrected continuation required the original order in a visible `role=status` element. Its English screenshot `P05_EN_RECONNECTED.png` shows “A previous submission was recorded as sale …, FCFA 10” and a server-verified recovery-lock release. The runner checked an unchanged financial snapshot before taking this screenshot and then printed the French-stage message. The French repeat was stopped because it incorrectly expected the same one-time notice after English reconciliation had consumed it: `acquirePOSCheckout` returns `recoveredSales` while settling the pending request, rather than retaining that notice indefinitely. The stopped continuation has no completed whole-run PASS. No additional sale was submitted.

The final post-fix harness uses a new synthetic fixture, preserves the pre-fix fixture as `PRE_FIX_BROWSER_FIXTURE.json`, captures original pending bytes after response loss, and reconnects in the same browser context. For the separate French presentation check it restores those exact captured bytes; this is an explicit fixture operation, not evidence of a second financial transaction or automatic language-switch persistence. Post-fix outcomes are determined only by `POSTFIX_BROWSER_RECOVERY.json` and corresponding screenshots.

Cold route compilation, failed sign-in/navigation deadlines, transient database connection failures and the test-only offline adapter's original one-shot socket suppression are retained in their dated artifacts. They are neither deleted nor counted as passes.
