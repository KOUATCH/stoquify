## Cross-cutting controls and provenance findings

1. `services/regulatory/regulatory-capability.service.ts:17` accepts authoritative capability and verification statuses separately. At line 55 a production request without both returns PENDING_COUNTRY_PACK; non-production at line 76 is marked NON_AUTHORITATIVE. `runtime/regulatory-runtime-class.ts:20` forces PRODUCTION when its deployment-class resolver identifies production, otherwise defaults to SANDBOX. This is a source-bound guarantee for callers of that port, **not an audit of every legacy caller or deployment's environment labels**. P21 must check consumer coverage and deployed classification before a release claim.
2. The pack's 2026 applicability and 2025 CGI reference need reconciliation against L02. This is a provenance freshness gap, not proof every stored value is wrong. Preserve historical rules; any future reviewed change needs a version/effective window and regression cases, not a blind hash refresh.
3. A source-check label and generated hash prove neither reviewer independence nor official approval. Some CNPS fixture notes say “regulator-confirmed” while their explicit reviewStatus remains SOURCE_CHECKED. Treat the structured draft/source-checked status as the current limitation; do not elevate prose to certification.
4. DGI e-services is not sufficient evidence for an individual payment provider's licence, merchant contract or technical protocol. The internal provider-code list is not a dated market availability list. Do not claim EU_MOBILE/YUP or every listed code is presently available.
5. A taxRegime string and a populated SYSCOHADA reference do not prove correct statutory treatment. P03's hundredths/thousandths are synthetic storage conventions, not a legal rounding rule.
