D06 Optional feature priorities
Canonical definition: Which optional lot/landed-cost/assets/budget/cohort features are required. [S1]
Choose which optional extensions are justified by an actual customer need. A promised optional feature becomes
required for that cohort.
Already confirmed
No acceptance of R34–R37 optional capabilities is established by the general modernization request. [S1, S8]
Proposal for your review
Proposed: assess each feature independently and defer those without a named customer decision, usable source
data and measurable acceptance scenario.
Alternatives and consequences
A bounded extension can satisfy a real sector requirement but adds implementation and assurance work. Deferral
protects delivery focus; it also forbids promising that feature for the selected cohort.
Evidence to inspect
Customer requirement, source-data assessment, bounded feature definition, cost/effort review and acceptance
example. [S1, S8]
Decision timing and deferral
Required / deferred / not applicable must be recorded for each feature, with reason and reassessment trigger. Do
not treat all optional features as one yes/no decision.
Accountable roles: Product + actual customer + domain owner. Review: Relevant
inventory/accounting/finance/data domain owner.
Due gate: R34–R37 before committing implementation capacity; earlier if promised to the first cohort.
